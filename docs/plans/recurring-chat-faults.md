## Claude continuation failure on 2 November

Read-only evidence is retained under `.diagnostics/recurring-chat-20261102-0349`. The original Claude conversation contains 575 own rows and ends with a weekly-limit error. Its six descendants (Devin, two Codex, three Claude) each have zero own messages and an unsent handoff. The last Claude descendant carries 581 inherited rows. Settings record the actual source and destination IDs and committed recipient mapping for the latest switch at 03:31:33. Its readable log has allocation/open headings but no prompt; reopening at 03:47:23 attempts resume and receives Resource not found. This disproves the hypothesis that the final Claude ID failed its first prompt on the limit, and supplies no evidence of an unrecorded replacement ID.

The confirmed cause is host publication before first interaction. Continuations stores the provider's session/new identifier, saves the handoff locally, transfers recipient ownership and marks the transfer committed without sending that handoff. Reopen then treats the untouched allocation as a resumable native conversation. That is a category error: inherited host history is not a provider conversation. The original limit error is preserved, but the later switch chain contains no new provider conversation to resume. No evidence establishes deletion of those provider IDs.

Claude's [session documentation](https://code.claude.com/docs/en/agent-sdk/sessions) describes conversation persistence and obtaining IDs from query results or initialization. The pinned adapter exposes session/new and session/resume; its allocation response is not a separate durable-publication signal. Dinah will not branch on whether an unprompted allocation happens to be resumable. The lead's 03:52 rule is authoritative: a zero-own-message node with an unsent handoff is freshly allocated on reopen, then its saved context is sent through a genuine continuation prompt. Only sessions with a host-recorded first prompt attempt can enter resume. The marker records submission intent before the call, not provider durability or delivery acknowledgement.

## Correction contract

The host records native prompt attempts, terminal failure and explicit resource-not-found refusals in settings. The refused identity includes its provider; ordinary opens and bus wakes consult the same gate. A refusal returns structured detail kind session-not-found, provider, sessionId and recoverable, without repeating resume. A recoverable missing conversation can automatically continue once into the same provider using the existing validated saved-history transfer. Failed first prompts or an incomplete automatic attempt require explicit recovery instead of recursively allocating more candidates. A limit failure never selects another provider. Settings and original history remain authoritative across restart.

An automatic continuation records its attempt before allocation, uses the existing recipient-preserving transfer journal and sends the saved handoff as a genuine request to resume the pending task. It never sends a dummy persistence probe, fabricates an ID or writes provider storage. If allocation or submission fails, it exposes one explicit saved-history recovery action, retains the failed candidate and original history, and makes no successful-recovery claim. Same-provider/model selection is preserved from saved options where supported. Explicit provider changes remain the person's choice.

Front End owns the session-not-found error presentation and integrated Release handoff. Engine owns the native lifecycle gate and focused first-prompt, missing-resume and repeated-reopen checks. The current incident's recovery uses the supported saved-history operation, with backups captured first. No restart or broad regression gate is part of this correction.

Paul confirmed that explicit Continue from Saved History repeatedly produced the next failed node. Both RecoverSession and RecoverSessionModel now start the genuine continuation prompt immediately after the saved-history transfer commits. They return the current activity snapshot. The page does not send the handoff. A failed or interrupted first prompt returns session-unverified on subsequent reopen; it never claims that the provider deleted or refused that allocation. The durable attempt guard prevents repeated automatic allocations after allocation or submission failure.
