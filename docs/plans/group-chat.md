# Group Chat Work After the Cleanup

Paul asked on 29 October 2026, after running the build that finished the [cleanup](cleanup.md), for three things: chats that keep their place in a group across a provider change, no turn limit to work around, and whatever else the cleanup showed. Dinah Architecture wrote this proposal the same day. Nothing in it is decided until Paul marks it up, and no code has been written.

## What Paul Saw: @everyone Reached One Chat at Once

Paul's @everyone after the restart (message 548) reached Dinah Architecture in 3 seconds, Dinah Front End Cleanup in 51 seconds and Dinah Engine Cleanup in 3 minutes 39 seconds. The bus's delivery records and the window's log say why. After Restart to Update the engine opens chats only when something needs them, and Architecture was the only one loaded, because Paul was talking to it. A group message to a chat that is not loaded opens it in the background, and opening it asks the agent to replay the chat's whole history (`session/load`) before the message is delivered. The two other chats have very long histories from the night's work, and their replays finished at 11:39:09 and 11:41:56, which is when each received the message.

Nothing was lost, but a group is unusable if a mention takes minutes to arrive. There are two separate fixes, and the first is the larger win.

1. **Deliver without waiting for the whole replay.** The engine waits for `session/load` to finish because the agent has to know its own history before it answers. The message itself could be queued for the turn that follows the replay, and the chat could show it at once as arriving, so the person sees the group working. That alone does not shorten the wait for the answer.
2. **Keep group members loaded after a restart.** A chat that belongs to a group with a recent message could be reopened in the background when the window starts, so a mention finds it ready. That costs an agent process for each such chat, and it should be bounded and choosable.

A third lever, a shorter replay, belongs to the providers, and Dinah cannot change how Claude replays a session.

## Keeping a Chat's Place Across a Provider Change

Switching a chat's provider (`Continuations.Continue` in `internal/sessionhost/continuation.go`) makes a new session with a new ID and marks the old one superseded. A chat's bus identity is stored against the session ID (`Settings.BusSessions`), and nothing moves it to the new session. The new chat therefore gets a new bus identity the first time it uses the bus, which belongs to no group, and the old identity stays a member of every group on behalf of a chat that no longer answers. That is why the Codex segment of this chat was refused when it posted to Dinah Cleanup ("this chat is not in the group chat; join it with room_join").

The fix is for the continuation to hand the old session's bus identity to the new one, so the chat's address, its group memberships, its unread messages and the links that trust it all carry over. It has to happen inside the continuation's existing commit point, so that a switch that is rolled back leaves the identity with the old session, and the old session must stop answering to it before the new one starts. The bus's own records do not change, which makes this a window change with a test for each of those cases.

## Removing the Turn Limit

The bus stops an automatic handoff after three hops, which is its guard against two agents waking each other forever. During the cleanup the guard stopped the group twice, because it also counts hops between chats of one workspace, and the remedy Architecture used was to let a workspace trust itself with a link that has no limit (`internal/bus/links.go`, 29 October). That works, but it means a group's ability to keep working depends on a link setting nobody sees, and a new workspace starts with the limit back in place.

A group chat has something a pair of agents does not: the person is a member and can see everything. I propose that the hop limit stops applying inside a group chat, and that a group gets a guard of its own that the person can see and change.

- **Inside a group, agents wake each other without a hop count.** The mention rule already decides who answers.
- **A group has a budget of agent turns since the person last posted**, shown in the group's header, for example "12 turns left before the group waits for you". When it runs out, mentions still deliver, but they no longer start turns until the person posts again. A post from the person refills it.
- **The budget is a property of the group**, with a default and an "unlimited" choice, so a long working session like tonight's can be set to run unattended and a casual group cannot run away.
- **Direct messages between workspaces keep the hop limit and trusted links as they are.** The self-link from 29 October becomes unnecessary for groups, and can be removed once the group budget exists.

This changes the bus's delivery rules, so it needs DESIGN.md updated with it and a migration that leaves existing links alone.

## Other Things the Cleanup Showed

These are in the order I would take them.

1. **Four intermittent test failures without a cause.** The terminal-close test, the cancelled-question test, the extensions suite's frame target and one browser suite on the final run whose name was not captured. They will hide a real regression sooner or later.
2. **The race detector cannot run here.** It needs cgo and a C compiler, so every concurrency argument tonight rested on reading the code and on mutation tests. Installing a compiler for test runs only, with the shipped build still built without cgo, would let the gates include `go test -race`.
3. **State events can arrive out of order.** Every engine event is emitted after its owner's lock is released, so two changes made at once can reach the page in the opposite order to the one they happened in, and the page shows the older state until the next change or resync. Provider state showed it, and it applies to sessions and settings too. A per-owner version number in each state event, with the page ignoring an older one, fixes it without moving any emit.
4. **A window opened on a running chat misses the current turn so far.** It draws the saved transcript, which can be stale by the whole turn, and then starts from the log's head. The chat event log can now supply that part.
5. **Replay disagrees with the saved transcript.** The log shows a warning whenever a reopened chat's replay holds a tool message the saved copy lacks, 113 times in the previous log. The replay replaces the saved copy, which is not nothing: the copy changes form after almost every reopen. The cause, found on 29 October 2026, is that the saved copy did not miss tool messages. It held a row for each event the Claude adapter streamed for a call, with titles that changed as the input arrived, and the replay of the adapter's history holds one merged row for the call, so the rows could never be equal (see Progress).
6. **The Git applet's changes check takes 20 seconds and repeats every 20 seconds.** It is probably a deliberate long wait for changes, and it predates tonight, but it is worth confirming that it is not a timeout firing on every call.
7. **Terminal scrollback,** deferred until Paul sees how often a terminal loses output.

## Proposed Order

1. Keep a chat's bus identity across a provider change. It is small, self-contained and fixes a defect Paul has already hit.
2. Group budgets in place of the hop limit inside groups, with DESIGN.md first.
3. Faster delivery to a chat that has to reopen, starting with showing the message at once.
4. The intermittent failures and the race detector, before anything else concurrent lands.
5. Ordered state events, then the running-chat gap and the replay disagreement.

The same three chats can do it: Engine for the bus and continuation work, Front End for the group header and the budget control, and Architecture for the design and review.

## Paul's Decisions

Paul answered on 29 October 2026 (message 557), and the plan is approved in the proposed order.

1. Paul wants no guard inside a group for himself, and expects other people to want one. A group therefore has a turn budget as described above, and the default is unlimited. A person who wants a guard sets a number for the group, and the header shows the budget only when one is set.
2. Chats that belong to a group are reopened in the background when the window starts, so a mention finds them ready.
3. A C compiler may be installed for test runs only, so the race detector can run. The shipped build stays without cgo.
4. The order stands: provider switch, group budgets, faster delivery, the intermittent failures with the race detector, then ordered state events and the rest.

## No Hard-Coded Providers or Models

Paul asked on 29 October 2026 (message 734), after a picture hint that mentioned Claude and Devin in an Ollama chat, for every hard-coded provider or model reference to go. The rule is that a provider's name, a model's name or a fact about what one can do appears only in that provider's own adapter and in the registry that lists the providers. Everything else reads them from the registry or from what the provider reports: display names, defaults, capabilities such as reading pictures, and limits such as context sizes. A test fails when a provider or model name appears in shared code or page text outside those places, in the manner of the existing test for the product's name. Engine takes the Go side and Front End the page. Each first posts an inventory of what it finds and what replaces each, before changing anything.

Another project's lead sharpened the rule the same day (message 736), and Architecture adopted its form. Text that is about agents in general never mentions a provider or model, and a claim about what a model can do comes from what it reports, as known, not, or unknown, with nothing shown for unknown. A surface that belongs to one provider, such as one provider's usage dialog or its sign-in, may mention that provider, but only through the registry's display name, so each name has one definition. Behaviour that differs between providers, such as whether removing a chat deletes or hides it, is decided by facts each provider declares in the registry, and the wording is built from those facts. The registry therefore gains a declared-facts surface as part of this work. The test excludes documentation, tests, wire markers and text addressed to agents, such as tool names.

Front End's inventory of the page (message 749) found about 160 lines a person reads or that decide behaviour, in ten groups, and Architecture accepted it with one change. The settings cards that belong to one provider (Codex approvals and sandbox, Ollama approvals and file access, Devin approvals and usage page, Claude's key, adapter and Node.js setup) are that provider's own surface, so they stay as written code and do not become sections the registry describes with control types and save calls, which would turn the registry into a form language for one screen. They move instead into one page module for each provider, which the test treats like a provider's adapter, and the shared Settings page draws the module of each provider the registry lists, with its title from the display name. Claude's Node.js setup and the other executable and sign-in wording go with them. The rest stands as proposed. A chat's provider comes from the chat's information rather than its ID, an unknown provider shows no name rather than Devin, the default provider comes from the registry, and the internal names such as restartDevin and devin-menu become neutral in the same pass. Status words, prices, the usage page, removal wording and the skill-sharing targets wait for the registry's declared facts, which Engine adds and the page reads at start from the providers record (AgentProviders) along with each provider's name, its default flag and its status. The page starts with the display names, the chat's provider and the fixed Devin text in the markup, which need nothing new from the engine.

## Opening a Chat Without Replaying Its History

Paul reported on 29 October 2026 that reopening a long chat still takes a minute or two: Dinah Engine Cleanup finished loading after about 108,000 parts. Reopening asks the agent for `session/load`, which the Agent Client Protocol defines as replaying the whole conversation to the client, oldest first, before the session takes a prompt. Those parts are for display only; the agent restores its own context from its own records. The protocol also defines `session/resume`, which "resumes an existing session without returning previous messages", available when the agent advertises `sessionCapabilities.resume`. Claude's adapter, version 0.87.0, advertises it and implements it.

Dinah Architecture proposes that a chat with a saved copy is reopened with `session/resume` whenever the agent advertises it, and that the page draws the saved copy at once, so the chat is ready in about the time it takes to start the agent. `session/load` stays for an agent without `resume`, for a chat with no saved copy, and as a command the person can run to reload the full history from the agent. The saved copy is in the same form a Claude replay produces since the replay fix, but it lacks two things a replay supplies: the agent's thinking and plan rows, which Dinah does not save, and the end of a turn that was cut off by a crash, since the copy is written when a turn ends. Paul approved it on 29 October 2026, with the fast resume as the default and loading the full history as a command. Engine proposes the shape before code, and the page's half (drawing the saved copy at once, and the command) is Front End's.
