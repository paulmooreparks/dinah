# Provider Names in Shared Engine Code

This is the Go side of the inventory of hard-coded provider and model names, made by Dinah Engine Cleanup on 29 October 2026 at Architecture's request, after the provider table (`cmd/dinah-desktop/provider_registry.go`) was built. It covers every comparison with a provider's name in the engine's shared code, which is everything outside the adapters (`internal/claudeagent`, `internal/codexagent`, `internal/ollamaagent`, `internal/agents`), the tests and the table itself. There are 107 such literals in 29 files, counted by the enforcement test (`internal/profile/provider_names_test.go`), which holds the list of them by file and lets it only shrink; an earlier count of about 115 in 35 files was made by lines and is replaced by this one. No model name appears in shared engine code, so nothing needs to be listed under models.

## What each group becomes

Each group says what the code asks, where the answer belongs and how many sites it has. A site that asks a fact becomes a read of the provider's row. A site that is one provider's own work moves into a file that belongs to that provider, which the enforcement test treats as that provider's adapter.

1. **Provider identity of a saved chat (about 12 sites).** A chat saved before chats had providers is Devin's, and a chat's provider is read from the prefix of its session ID (`normalizedProvider`, `providerForSession`, and the same fallback in `internal/sessionhost` conversation, history, lifecycle and runtime). This becomes one named constant for the legacy provider and a session prefix on each row, so the mapping is data. It is a legacy rule and stays a rule, but in one place.
2. **Facts that already have a field (about 25 sites).** Whether a provider has prices and its price events (`devin_prices.go`), its own commands and the filtering of slash commands (`skills.go`), where its usage page comes from (`usage.go`), whether it signs in and with what words (`auth.go`, `providers.go`), whether its executable can be chosen (`providers.go`), which providers a picture question goes to (`attach.go`) and whether a provider is available once installed (`providers.go`). Each reads the row.
3. **Facts that need a field the table does not have yet (about 20 sites).** Which providers receive Dinah's managed servers when a chat opens (`internal/sessionhost` session lifecycle, twice, which today means everyone but Devin), which providers can take steering (`steering_io.go` five sites and `internal/hooks/steering.go` one), whether a provider reports tool call IDs that the transcript capture matches (`transcript_capture.go`), the source label of a provider's commands (`handler_updates.go`), and the one provider whose journal has its own folder (`journal.go`, `internal/sessionhost/journal.go`). Each is a boolean or a short value on the row, added when the site is changed.
4. **Tables keyed by provider (about 15 sites).** The file limits (`file_limits.go`), the continuation budgets (`continuation_budget.go`), the approval modes (`applet_consent.go`) and the adapters (`provider_lifecycle.go`, which is the wiring table of what to start). These are data keyed by an ID. They move into the row as fields, except the adapter table, which stays beside the row as the one place that says how to start each provider.
5. **One provider's own work (about 30 sites).** Finding and checking each provider's installation and setup (`providers.go`, 20 sites), Devin's options and substitutions (`options.go`, `option_substitutions.go`, `session_lifecycle.go` in the window), Claude's account (`provider_account.go`), Ollama's approvals and file scope (`ollama_approvals.go`), Devin's applet registration paths (`applet_registration.go`) and Codex's sign-in event (`sessionhost/handler.go`). These move into one file for each provider in the window's package, each as that provider's adapter module, and the shared code calls them through the row.
6. **Settings that mention a provider by name (about 6 sites).** `settings.go` has a constant `ApprovalsDevin` and `app.go` migrates a default provider that is not Devin. The constant is a stored value that cannot change without a migration, so it stays and is listed as an exception. The migration reads the legacy constant from group 1.
7. **Not provider names (3 sites).** `internal/profile/profile.go` is where the product says which providers it offers, which is its job. `cmd/dinah/main.go` has the command line's `claude` and `codex` subcommands and the two lookups for their programs, which are those programs' own launchers. Both are exceptions with the reason given.

## Order of work

The row already carries the facts of group 2, so those sites change first, then group 1, which only needs the constant and the prefix. Groups 3 and 4 add their fields one at a time, each with the site that reads it. Group 5 is the largest and is moved last, one provider at a time.

## Exceptions for the enforcement test

The test has built-in exceptions for the adapters and for three files: the table itself, the command line's launchers and the stored constant `ApprovalsDevin`, and the profile is skipped as the place the product says which providers it offers. The legacy-provider constant with the session prefixes becomes the fifth when group 1 is changed. The sites still to change are listed in the test by file and count, may only shrink, and any other occurrence of a provider's name in shared code fails it.
