# Cleaning Up Before the Next Features

Paul said on 28 October 2026 that Dinah needs cleanup before more features go on top of it, and asked how the work should be planned. This plan is a proposal for him to mark up. Nothing in it is decided until the Decisions section at the end says so.

## Why Now

Dinah has taken 250 commits in seven days, and most of them added behaviour. The design document's own review of 23 October asked for one shared piece for each task the code solved several times over (one provider lifecycle, one JSON-RPC transport, one process runner, one way to change settings), and the code has instead grown more copies of each since then. A survey of the source on 28 October found the shapes below. None of them is a defect a person can see, which is why they have been easy to leave, and every feature added on top makes each one more expensive to remove.

The plan is ordered so that each step is also the first step of the daemon, milestone 7 in DESIGN.md, which is where the engine moves out of the window. Cleanup done without that in view would be done again when the daemon comes, and the DIRT principle says to choose the shape that is not redone.

## What the Survey Found

### In the window's Go code (`cmd/dinah-desktop`)

- **Four provider lifecycles.** Devin runs on fields of its own on the App (`conn`, `init`, `trace`, `gone`), while Claude, Codex and Ollama share a providers map. The start sequence (prepare applets, start the process, initialize, watch for exit) is written four times, and the teardown that follows a process exit is written four times with small differences; the Devin path closes the chat log and the shared path does not.
- **Three JSON-RPC transports.** `internal/acp`, `internal/codexagent` and `internal/ollamaagent` each have their own reader, pending-call map and decode helpers. Process hiding and the `DINAH_HOSTED` environment variable are each written in three places.
- **The page can call anything exported.** The bridge reflects about 270 exported App methods onto the page. The ACP notification handler is among them, so the page could inject a synthetic agent update. New methods are classified for the exit guard by hand, and an unclassified one counts as unfinished work, which is sound, but the surface is wide and grows with every feature.
- **The readiness guard is repeated.** The test of whether a chat may take input (`switching || superseded || restoringOptions || replaying || !open`) appears in nine places with one variant.
- **Settings change by two routes.** `updateSettings` is described as the one way, and about forty call sites still change the struct in place and save.
- **The bus is opened per call.** The window's helper opens and closes the SQLite file for each operation, including on every turn and every doorbell check, and each open re-runs the schema and migration checks. Only the watcher keeps a handle.
- **One App struct, one Notify.** `App` has about twenty mutex-guarded groups of fields. `Notify` is 212 lines and handles redaction, subagents, background tasks, replay, transcript, chat log, journal, capture, options, commands and titles in one body.
- **Two MCP SDKs.** The bus server and the extension host use the official Go SDK; Ollama's tool loop and the dinah-applets helper still use mark3labs.
- **Digests are hashes of embedded source.** The chat applet's digest covers `session.go`, `steers.go`, `bus_chats.go`, `bus_wake.go` and `chat_ask.go`, so an edit to turn handling changes what agents must rediscover.

### In the front end (`cmd/dinah-desktop/frontend`)

- **app.js is the shell and the chat.** Six thousand lines in one closure hold the menus, Settings, Workspaces, Packages, Notifications, Find and a 2,600-line chat controller, sharing variables such as `sessions`, `active` and `workspace`. A `$` helper falls back to the current chat's DOM, and twenty top-level shims forward to whichever chat is current, so what a host-level call affects depends on focus. editor-applet.js has the same shape with a 2,000-line `init`.
- **Four command mechanisms.** PUDL's own commands, `commands.js`, a `data-cmd` click switch of about fifty cases in app.js, and the `commands()` each applet returns to the workbench.
- **Helpers copied per file.** Twenty-four files define their own bridge accessor, nine their own error-message helper, five their own node builder, and app.js defines four formatting helpers twice.
- **Events bypass the shared subscription.** Several modules call the runtime's event registry directly rather than through the host's single subscription per name.
- **Ninety-one copies of the Go stub.** Every browser suite stubs the bridge inline, so a change to a bridge method's shape is an edit across many suites.
- **Two styles.** Most files are ES5 with `var` and generous comments. extensions.js, theme-editor.js, appearance.js and exit-guard.js are ES2020, and extensions.js has lines of about a thousand characters.

### Across both

- **The event stream has no replay.** A page subscriber whose 256-event buffer fills is dropped, the browser reconnects, and the events in between are gone with nothing to resync. The remote-control proposal already needs sequence numbers and a cursor; so does the daemon.
- **State a daemon must own lives in the window.** The agent processes are tied to the window's job object, the bus watcher runs in the window, the set of outstanding chat questions is in memory and anything not in it is withdrawn as an orphan, the applet broker runs in the window with the MCP helper as a stdio bridge back into it, and the extension host runs in the window.
- **The bus reads the window's settings.** The person's name and the workspace list are read from the desktop's `settings.json` by shared packages, so that file is an unwritten contract.

Not everything found is debt. Two Markdown renderers (markdown-it in the page for streamed chat, goldmark in Go for documents) exist because streamed text is drawn chunk by chunk in the page and documents are parsed once in Go, and the two sanitisers serve different content. The plan leaves both as they are and records the choice.

## The Rule for Every Step

Paul works inside Dinah all day, so every step obeys the same rule the update path obeys. Each step is one or a few commits, each with the Go tests, vet and every browser suite passing, each installable with Restart When Chats Finish, and each small enough to revert alone. No step changes a saved file's format, a bus table, an applet action's name or schema, the extension contract or anything agents are told, unless the step says so and says how older data is read. Behaviour the person can see does not change during cleanup, and the browser suites are the check that it has not.

## Phase 0: Make the Refactoring Cheap

These come first because every later step pays for them.

1. **One Go stub for the browser suites.** A shared fixture under `e2e/lib` that builds the stubbed bridge from a table of methods and events, which each suite extends rather than rewrites. The 91 inline stubs move onto it suite by suite, starting with the chat and settings suites that the app.js split will touch. A bridge method changing shape is then one edit.
2. **A reliable full run.** The terminal-close test has timed out under the parallel run since at least 25 October and passed alone each time. Find the reason or move it behind a tag, so that a red run means something. The page-view and chat-scrollback suites that fail under load for timing reasons get the same treatment.
3. **An inventory check.** A Go test that lists the exported App methods and fails when one is added without an entry in a table that gives its exit-guard class and whether the page may call it. This is the allowlist that phase 1 narrows the bridge to, started as a test so that no method is reclassified by accident along the way.

## Phase 1: One Engine Behind the Window

The Go steps are ordered so that each removes one kind of duplication and leaves a seam the daemon will use.

1. **One provider lifecycle.** A `provider` type with start, initialize, watch and teardown, and four adapters behind it. Devin's fields on the App go, and Devin becomes an entry in the providers map like the others. The four teardowns become one, and the chat-log close that only Devin's path did is done for all or for none, decided when the code is read. The auth failure that today reports every non-ACP connection as Codex is fixed in passing, since it is the same branch.
2. **One JSON-RPC transport and one process start.** `internal/acp`'s connection becomes the transport Codex and Ollama use too, and the pending map, decode helpers, hidden-window start, job-object tie and `DINAH_HOSTED` injection live once. The ACP wire types stay where they are.
3. **One readiness predicate and one settings path.** `Session.ready()` replaces the nine copies, and every settings change goes through `updateSettings`, which then becomes the only writer. This is small and mechanical, and it goes before the extraction so the extracted code is already clean.
4. **One bus handle.** The window opens the bus once and the watcher and the per-call helper share it. The schema and migration checks run once per process.
5. **The ACP handler leaves the App.** `Notify` and `Request` move onto a handler type that the connections are given, with `Notify` split by update kind. The page can no longer reach them, and the App stops implementing the agent's interface.
6. **The page API becomes explicit.** The bridge serves the methods in the phase 0 table and nothing else. The App keeps its methods, but the bridge no longer reflects over the whole struct.
7. **The engine packages.** Sessions and turns, the bus watcher and waking, the applet broker host, the extension host and the terminals move from `cmd/dinah-desktop` into packages under `internal/`, with the App holding one of each and the page API calling into them. This is the largest step and the one that makes the daemon a transport question rather than a refactoring question. It is done one package at a time, terminals first because they are the most self-contained, sessions last because everything else touches them. The engine's state folder layout does not change.
8. **One MCP SDK.** The dinah-applets helper moves from mark3labs to the official SDK that the rest of Dinah uses. This is independent of the rest and can go anywhere in the phase.

After step 7, chat discovery digests cover the extracted implementation and retained shell adapters that determine action behavior. Extraction does not remove turn handling from those inputs; implementation changes must still invalidate discovery.

## Phase 2: The Front End

The front-end steps are independent of phase 1 and can run beside it in another chat, since they touch different files. The suites in phase 0 are the shared prerequisite.

1. **Shared helpers.** One file for the bridge accessor, the error message, the node builder and the formatters, and every file uses it. Every event subscription goes through the host's single subscription per name.
2. **app.js is split**, in this order, each a commit: the session store and lifecycle; Notifications and questions (the generic model already exists in `notices.js`); Settings; Workspaces with import and export; Packages; Find and Open; and last the chat controller into `chat-applet.js`, with mentions, the skills form and templates as files of their own. What remains in app.js is the host object and startup. The `$` fallback to the current chat goes with the controller, and the twenty forwarding shims go with it.
3. **One command mechanism.** The `data-cmd` switch moves into `commands.js`, which already declares the menu bar, so a command is declared once and the menus, Keyboard Shortcuts, command search and agents read the same table, as DESIGN.md says they do.
4. **editor-applet.js is split** along its own section comments (head, views, draft, saving, preview, suggestions, text, find, keys, clipboard, commands, opening).
5. **One style.** extensions.js is reformatted to the codebase's layout, and the ES level is decided once (see Decisions) and applied as files are touched, not in a sweep.
6. **Markup follows its applet.** The live Settings, chat and Notifications markup in index.html becomes templates owned by their applets, so a view's DOM is in one place. This is last because it is the least urgent and the most visible if it goes wrong.

Classic scripts and `window.dinah*` globals stay in this phase. Moving to ES modules is a real improvement and a separate step, after the split, because the split is what makes the module boundaries visible, and because the browser suites' stubbing and the Content Security Policy both need checking against module loading.

## Phase 3: What Both Sides Need

1. **Sequenced events with resync.** Every event the bridge emits carries a sequence number, a subscriber that reconnects sends the last one it saw, and the server either replays from a bounded buffer or tells the page to refetch its snapshot. This is required by the daemon, by remote control and by a second window, and it fixes today's silent loss when a subscriber is slow.
2. **The bus stops reading the window's settings.** The person's name and the workspace registry move to a file the shared packages own, or the window writes them into the bus, so that `settings.json` is the window's alone.
3. **The daemon.** With phases 1 and 3.1 done, the daemon is the engine packages behind the bridge's transport in a process of their own, and the window is the page server and the native shell. That is milestone 7 and is planned in its own document when phase 1 is done.

## What Is Left Alone, and Why

- The two Markdown renderers and two sanitisers, for the reason given above.
- The bus's polling (the one-second watcher and SSE). It is simple, it works, and the daemon changes where it runs rather than how. A change notification from SQLite is not documented behaviour to rely on.
- The CLI's own bus page in `internal/web`. DESIGN.md already says the bus's views moved into the window; the page can go when Paul stops using `dinah serve`, which is a product decision rather than cleanup.
- The 3.5 MB Mermaid bundle and the unused PUDL `min/` folder. They cost disk, not correctness, and PUDL.md says the whole distribution is copied on purpose.

## How the Work Runs

Phase 0 is one chat's work for about a day. Phase 1 is the long pole, roughly a week of agent work at the current pace, with step 7 taking half of it. Phase 2 runs beside phase 1 in a second chat and is shorter, three to four days. Phase 3.1 and 3.2 take a day or two after both. These are relative sizes rather than promises; the browser suites decide when a step is done.

During the work, features wait. The exception is a defect that stops Paul working, which is fixed on top of whatever step is current. Ideas that arrive go into `docs/dinah-ideas.md` as they do today.

Each step's commit message says which step of this plan it is, and this document's Progress section records the step when it lands, as the other plans do.

### Rulings on the working chats' questions

Dinah Architecture ruled on 29 October 2026.

- **Phase 1 step 1.** A `providerAdapter` interface with four implementations and one `startProvider` doing the shared sequence; Devin moves into the providers map and its four fields on the App go; `watchProvider` becomes the only teardown, matching sessions on the normalized provider, and closes the chat log for every provider. The auth prompt looks its provider up from the connection, so Codex keeps its ChatGPT prompt and Claude and Ollama get the plain sign-in error. Two behaviours that only Devin had become every provider's: a start or initialize failure emits the failed state, and a stopped detail includes the process's error, since the only thing the person newly sees is a notice of a failure they were not told of before. Only Devin writes the protocol trace until step 2, where tracing becomes an option of the one transport.
- **Phase 2 step 1.** The event hub is created in the early shared helpers file as `dinahHost` itself, the same global, so modules that load before app.js subscribe through it; app.js attaches its agent-event queue routing, with the render scheduler's batching unchanged, and extends the same object with its other services. A subscription made before app.js runs receives events after it, there is one runtime subscription per event name, and no module calls the runtime's event registry directly.

- **Phase 2 step 2 test readiness (29 October 2026).** Architecture approved waiting for the expected initial chat row in `app-ui3` before its unchanged assertion, provided launch readiness does not promise completion of the session list. The wait uses the existing timeout and fails if the row never arrives. Fixed sleeps, whole-test retries and startup behavior changes are excluded. The final extraction must pass the focused suite and full browser run.
- **Phase 2 step 6 shape (29 October 2026).** Architecture chose to keep the markup as HTML (message 499). The chat, Settings and Notifications markup becomes `<template>` elements in index.html, grouped at its end under a comment heading for each applet, and the code in `setupChatWindows` that lifts live markup into a template at startup goes. That meets the step's purpose, which is that a view's DOM is written in one place; the file it sits in matters less. Markup held as JavaScript strings was rejected, because it moves static structure out of HTML, where the Architectural Principles keep it and where the browser and editors check it, into strings that need escaping and that nothing validates. Content, order and IDs stay the same, and the proof is a browser run comparing the serialized DOM of each template and of `#applet-storage` before and after, plus the full gates. If the page is later assembled on the server, the templates can move to per-applet files then.
- **provider-turn-lock readiness (29 October 2026).** On the same terms as `app-ui3`, Architecture approved waiting for the opened chat's session snapshot to be applied before the suite's "codex composer shows the active turn" assertion, which is unchanged. The wait uses the existing timeout and fails if the snapshot never arrives. Fixed sleeps, whole-test retries and startup behavior changes are excluded.
- **Phase 2 step 4 boundary (29 October 2026).** Architecture approved Front End's proposal (message 464). Each editor window has one state object, `ed`, holding only the state and helpers that a scope scan shows crossing section lines. Each section file registers a factory on `window.dinahEditorParts`, and `init` installs the returned functions onto `ed` under their current names, with flat names rather than per-part namespaces until ES modules. Installing a name that already exists on `ed`, whether a function or a state field, throws. Shared state is read and written through `ed` at call time; no part copies a shared value into a local. State private to a section lives inside its factory, never at the top of its file, so two editor windows never share it. A part that owns a timer, listener or other resource returns a teardown that `init`'s dispose path calls, so closing a window releases everything it did before. The commits are A (module-level pieces), B (the conversion to `ed` in place, with the full list of shared names and the reason for each in its review post) and then one section per commit, find first. Commit B is done on Claude, and the section moves may run on another provider. Nothing visible changes, and each commit passes the full browser gate.

## Decisions

Architecture approved a separate question-posting correction after Engine's deterministic reproduction in message 350 on 29 October 2026. On unchanged master, cancellation immediately after SQLite commits can make Ask's subsequent Message read fail, returning no ID although a pending delivery exists. The caller therefore cannot register the question or install its withdrawal defer. Capture the Message through the insertion transaction using the existing selector and scanner, and return it only after successful commit, with no fallible read afterward. Preserve the existing empty attachment representation. Tests must cover rollback before commit and successful commit followed by cancellation, and prove the returned ID permits normal registration and withdrawal. The original intermittent failures are still not conclusively attributed to this reproduced path. The correction must be reviewed independently before the bus extraction proceeds to merge.

The cancellation failure recurred during Engine's bus extraction in message 348 on 29 October 2026. Architecture requires diagnosis before approving that extraction, even if the isolated rerun passes. The test invokes the chat handler directly, and that handler returns through askOverBus's deferred dropQuestion, so broker cancellation returning early does not explain this test. Compare unchanged master and inspect withdrawal errors and database state at the failed assertion. The current drop path logs withdrawal errors and returns; whether such an error caused either observed failure remains unverified. Preserve assertions and failure logs, and keep any correction separate from the extraction.

Architecture approved the bus-service and scheduler boundary in message 346 on 29 October 2026. `internal/bushost.Service` owns the bus handle, watcher lifecycle and round bookkeeping, including pending-question registration and orphan withdrawal under one dedicated mutex. Watcher round order and callbacks remain unchanged; host callbacks run outside service locks. Failed handle opens remain retryable, and a closed handle cannot reopen. Stopping and joining the watcher is distinct from closing the handle after sessions leave the bus.

The wake scheduler owns queue and connection bookkeeping but has no host callbacks or Session pointers. Its caller must serialize every scheduler read and mutation under the session authority's lock. App.mu continues to cover collecting live-session values and making scheduler admission or completion decisions as one transaction, so pending opens and live background chats cannot exceed the existing combined limit. Returned decisions use copied values, and events, reconnects and unpark operations occur after the transaction. This lock ownership will move with the final session extraction. Session lifetime, provider shutdown and close wait groups stay in the adapter for now. Tests must cover concurrent completion/window changes against admission, pending-question atomicity and the two shutdown phases. The existing cancellation failure remains open; extraction does not authorize weakening its assertions. Extracted wake sources remain covered by chat action digests.

Architecture approved the maintenance follow-up proposed in message 340 on 29 October 2026. The broker host owns one maintenance goroutine with stop and completion signals. It watches the initial broker once, prunes immediately and waits 24 hours after each prune, including when that broker is later retired. Initial failure ends maintenance without retry. Close prevents new broker acquisition or maintenance startup, stops and joins maintenance, joins catalog loads already admitted, then closes retired brokers in order and the current broker. Concurrent Close calls share completion; callbacks and waits run outside the state lock.

Admission to catalog loading must be synchronized with shutdown before revision lookup or any loader callback begins. Tests must hold those callbacks and pruning in flight while Close starts, then release them and verify no broker publication or watcher restart occurs. Close may wait for an already-running load or prune; this change does not promise cancellation of those operations or of running invocations. Log wording, retention policy and digest coverage remain intact, including any new maintenance implementation files.

Architecture approved the broker-host extraction proposed in message 338 on 29 October 2026. `internal/applet/host.Service` owns broker construction, catalog revision, current and retired generations, invalidation and execution inspection. Built-in bundles precede extension bundles, and registry validation and extension-load reporting retain their behavior. State location, loaders, revision lookup, events and consent are injected. App retains consent decisions, action adapters, MCP authentication and transport, native export and presentation. Source digest inputs must include the extracted implementation as well as retained adapters.

Invalidation retires a broker without closing active work. Inspection and closing operate outside the service lock on snapshots, retaining shutdown order and the existing meaning of Broker.Close. Construction and callbacks must not introduce lock re-entry through App or extension hooks. The initial broker's watcher and daily retention loop may remain unchanged for this mechanical commit. That is a recorded lifecycle limitation, not a shutdown guarantee: the loop keeps its initial broker and has no stop signal. An immediately following, separately reviewed phase 1 step 7 change must give maintenance an explicit owner, stop and join it at shutdown, and prevent maintenance from restarting after close, while preserving pruning policy and cadence. Engine must propose that lifecycle change before implementation; step 7 is incomplete until it is resolved.

Architecture approved a deterministic regional-test fixture on 29 October 2026 after message 330. The late-locale case resolves HostLocale after 2500 milliseconds but assumes it is still pending after browser interactions and sleeps. Engine owns the correction in `e2e/regional.js` as a separate test commit: hold that response with an explicit fixture resolver, wait for the initial chat and notification times to render, assert the locale is pending, then release it and check the existing reformatted results with bounded condition waits. Architecture approved the extension service boundary in message 328 on 29 October 2026. `internal/extensions.Service` owns its Manager, command reviews, prepared-terminal tickets and install/library orchestration. Host callbacks supply workspace resolution, notification persistence, events and catalog invalidation, and run outside the service mutex. Existing IDs and aliases remain valid, aliases share an action without duplicate search or shortcut entries, and menu placements retain their labels, order and mnemonics. This boundary consolidates host declarations while preserving scoped applet contracts.

### Terminal extraction boundary (29 October 2026)

Architecture approved Engine's terminal boundary in message 317. `internal/terminals.Service` owns terminal sessions, locking, IDs, shell discovery and selection, profile resolution, environment normalization, PTY creation, output pumping and close operations. Both shell and prepared-command launches use its registration and pumping path. The service receives product display data, an event sink and a warning callback. Callbacks run without the service's map lock held; the process-wide warning retains its existing scope.

App owns one service for its lifetime and retains workspace/resource folder resolution, settings persistence and extension ticket authorization and expiry. Public method names, JSON shapes, saved profile fields, validation and terminal event payloads remain unchanged. Native standard-handle setup stays in the shell entry point. The extraction leaves platform behavior and `internal/pty` unchanged.

Close remains asynchronous and idempotent. CloseAll preserves the existing snapshot-and-concurrent-close behavior and waits for those Close calls; it does not newly promise that all output pumps or exit callbacks have finished. Tests move with their owning behavior without exposing PTY internals for test access. The existing terminal timeout remains an open investigation, and its assertions and deadlines must survive the move. Engine will submit this extraction as one reviewable commit with the full validation gates.

Architecture approved the single session/provider owner proposed in message 356 on 29 October 2026, with the first prerequisite cut authorized for implementation. `internal/sessionhost` will own live conversations, provider lifecycle, the ACP handler, turns and steering, waiters and conversation persistence coordination. App retains page adapters, settings storage, workspace/resource policy and native presentation. Dependencies must be named operations or snapshots; no generic App callback or second session registry is allowed.

The existing App.mu may be injected as the shared state authority throughout this extraction. Runtime operations must state whether they acquire that lock or require it held. Settings callbacks that acquire the same lock must run after it is released; an operation needing an atomic settings/session view must receive its snapshot within the existing transaction. Preserve per-session and steering lock order and document callback re-entry restrictions. Scheduler admission, completion and live-session state remain under the same authority. Do not change existing lock-held I/O or shutdown guarantees incidentally; report any necessary behavior change separately.

The proposed sequence is value types and persistence primitives, live state and scheduler integration, provider lifecycle and handler, turns and steering together, then remaining orchestration and removal of temporary adapters. The live-state cut needs a concrete API and caller migration map before implementation because the later turn and handler cuts still access that state. Temporary adapters must delegate to the sole owner without exposing mutable records or maps. Move only prerequisites needed by the next cut. Keep prompt waiters, locks and mutable turn internals private rather than exporting them merely to cross the package boundary. Public aliases must preserve JSON and saved representations, including omitted and nil fields.

Each cut requires independent review and full gates.
