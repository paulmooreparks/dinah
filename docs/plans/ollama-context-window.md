# An Honest Context Window for Ollama Models

Another project's lead proposed this design to Dinah Architecture on 29 October 2026, from a requirement Paul set the same day. It is shared provider behaviour, so Dinah builds it first. This document records Dinah Architecture's rulings on it. The proposal itself is the specification, and it extends the context-length change recorded under "Ollama's Context Length" in [group-chat.md](group-chat.md).

## Accepted

The design is accepted into the Ollama adapter and the chat page, sequenced after the 29 October change, which is already merged. Its three parts stand:

1. **A ladder for each model.** The Context option offers doubling sizes up to the model's own `context_length` from `/api/show`, with that maximum always the top entry and "Ollama's setting" first and the default. A model that reports no limit gets a short conservative range that says Ollama did not report one. This also removes the fixed 256K ladder, which is one of the hard-coded values Paul asked to be rid of.
2. **The effective window.** It is the chosen size, or on Ollama's setting the model's maximum for a cloud model, which Ollama documents as the default for cloud models. For a local model on Ollama's setting the window cannot be read, and the meter keeps its "model's limit" wording with the caveat.
3. **An action when a known window fills.** Paul ruled that the default is to set the oldest turns aside and continue, with a marker in the transcript and the saved record kept whole. Compacting into a continuation through the existing handoff path is always offered beside it, and the person's choice is remembered for each chat.

## One Change: Act on Measured Counts

The proposal says the action happens "before a send that would pass" the window. The next request's size is not known until the model has counted it, and estimating it with a tokenizer of our own would be a prediction about Ollama's count, which the proposal itself rules out. The trigger is therefore measured. After each request Dinah has `prompt_eval_count` and `eval_count`, which Ollama reports as the tokens it processed. When those for the last request reach 90% of the known window, the next send is held and the person's chosen action runs first. The 80% note stays as the earlier warning, on the same measured counts. Setting turns aside then removes the oldest whole turns until the last measured request, less what they cost when they were sent, is below 80% of the window. What each turn cost is recorded as it happens, so this needs no estimate either.

Because the trigger reads the last request's counts, it lags by one request, and a single large turn can pass the window before the hold engages. The proposal's author pointed this out on 29 October when accepting the change. The 10% headroom covers ordinary turns, and setting turns aside repairs the rest from their recorded costs. The marker and any note about the window therefore say what Dinah did, such as how many turns were set aside, and never claim the window was not crossed.

## The Marker and the Event Model

The "turns set aside" marker needs no new kind of event. It is a status line in the transcript, emitted through the chat's numbered event log like any other transcript event, so a resync, a window opened late and the future daemon all see it through the paths they already use. The set-aside turns stay in the saved record, flagged, and the adapter leaves them out of the request it builds. The record's format gains that flag, and the record's revision number covers it.

## When the Window Is Known

The accepted design called a cloud model's window known on Ollama's setting, because Ollama documents that cloud models are set to their maximum context length by default. Engine found on 30 October that nothing documented says which model is a cloud model. The cloud page and its announcement show names ending in ":cloud" and in "-cloud" as examples, but no sentence states a rule, and the API reference does not document the remote_host field. So the window is known only when the person chose a size, and a chat on Ollama's setting, cloud or local, shows the model's limit with the caveat that the server may be lower, and is never held. Choosing the model's own maximum in the Context option gives a cloud model the same window it has by default and lets Dinah manage it. The documented signal that would change this is a field in /api/tags or /api/show, or a stated naming rule, that identifies a cloud model, or for a local model a way to read the size the server is set to.

Paul overruled this on 30 October (message 795): Dinah depends on the naming convention, because every cloud model he has seen ends in ":cloud" or "-cloud" and no local one does. It is a deliberate, named exception to the rule against relying on undocumented behaviour, and it is kept small so that it is easy to find and easy to remove. The convention is applied in one function in the Ollama adapter, whose comment says it is a convention Paul accepted and not a documented contract, and a model whose tag is "cloud" or ends in "-cloud" is taken to be a cloud model, whose window on Ollama's setting is its own context_length. If the convention is wrong for some model, the cost is bounded: Dinah holds at 90% of the model's maximum while the server may be smaller, which is no worse than having no hold. When Ollama documents a signal, the function changes to read it.

## The Page's Contract

Front End proposed the contract on 29 October (message 781), and Architecture approved it with one simplification (message 782). The usage update gains windowKnown beside size, because a cloud model on Ollama's setting has a known window and a local one does not, and the meter shows Over only when the window is known. A held send is in the chat's information as hold, with its kind, the counts, the two actions and the remembered choice, so a resync and a window opened late see it, and the held message stays in the engine's queue. A chat with a remembered choice is never held, because its choice runs and the marker is shown. A chat with no choice waits, and a card offers setting the oldest turns aside (marked as the default), compacting into a continuation, or starting a new chat. Picking on the card always remembers the choice for that chat (ResolveHold(id, action)), and "Ask Me Again About a Full Context" in the chat's menu clears it (ForgetContextChoice(id)). A model that reports no limit says so in the Context option's description. The chat's information also has choice, the remembered action or nothing, which the menu entry reads, and the hold itself does not repeat it. The marker and the 80% warning arrive as agent:update events of the kind dinah_status, through the chat's numbered log, and each is recorded in the saved copy and drawn once.

## Who Builds It

Dinah Engine Cleanup builds the adapter's half: the ladder, the window, the measured trigger, setting turns aside with the flag and the marker, and the remembered choice. Dinah Front End Cleanup builds the page's half: the option's entries, the meter's states and the hold with its choices. Each half comes back for review with tests, including a model that reports 1M, one that reports no limit, a cloud model on Ollama's setting, and a chat that reaches 90% and has turns set aside with the marker shown once.

## A Compaction Blocked by the Queue

On 30 October Dinah Front End Cleanup's chat filled its window with three messages queued, and neither course on the hold card worked. Engine found the cause (message 1072). A continuation is refused while anything is queued, and compacting took only the held message out of the queue, so the other queued messages blocked it every time. The failed course then left no hold in the engine while the page kept the card, nothing started the queue again, and the error was not logged. A compaction now takes the whole queue and sends every queued message to the new chat in order. A course that fails restores the queue and the hold, tells the page and logs the reason. The hold offers setting turns aside only when the adapter says a turn could be freed, which it cannot for turns recorded before costs were kept.

Queued messages were held in memory only, so a restart or a crash lost them. Paul decided the same day that they are kept on disk with the chat and picked up again after a restart (Engine).


### Queued Messages Are Kept: Built

A chat's queued messages are kept in one file for each chat in the state folder's queues folder, written whole and atomically by a writer that never blocks the chat, and removed when the queue is empty. Each message keeps its text, label, content blocks, delivered bus messages, pictures and steering ledger place, and has an id of its own that survives being carried to another chat. A waiting question from another chat is not kept, and a steer that was waiting is kept first. When a chat is opened its file goes back in its queue ahead of anything typed while it loaded, before it takes a turn, and the hold of a full window is not kept, because the first restored message goes through the same check as any send. A chat's file is not written while it waits to be restored from, so messages typed while a chat loads cannot replace it. A compaction keeps the messages it is carrying in the earlier chat's file until the new chat has them, so a crash while they travel loses none, and the messages found in two files are recognised by their ids. At start a sweep deals with chats that are not open: a chat that was continued has its messages added to its continuation once, and a deleted chat has its messages discarded and their text shown once in Notifications, while a closed chat's file waits until the person opens it (Paul, message 1074). A file that cannot be read is set aside with a .bad ending, the chat opens with an empty queue, and Notifications says messages may have been lost. A provider that stops drops a chat's queue from memory and not from disk. One window remains: a crash after a carried message has started its turn in the new chat and before the earlier chat's file is settled would run it twice, which takes milliseconds.

The one window left in that design is closed. When a queued message's turn starts in a chat, the chat's saved copy records the message's id (the last 256 are kept, in `startedQueueIds`; copies saved earlier lack the list), and restoring the file of a chat that was continued leaves out the messages the continuation's saved copy says have started, whether the continuation is open or closed. A message carried to the new chat and run there is therefore not run a second time after a crash that left the earlier chat's file unsettled.
