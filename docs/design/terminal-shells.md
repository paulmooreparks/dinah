# Terminal shell selection

## Ctrl+C investigation, 25 October 2026

Paul reported that Ctrl+C did not stop a Node mockup server in PowerShell 7, with no terminal selection. The browser regression confirms that Ctrl+C copies selected text and clears the selection; without a selection it sends byte 0x03 to TerminalWrite. A Windows integration regression starts a Node HTTP server inside PowerShell, sends that byte, waits for the shell prompt and runs another command successfully. Both checks passed. The reported failure remains unreproduced, pending the exact server launch command; no input-routing change was made.

Tools > New Terminal is one submenu with Default Shell first and the current shell catalog below it. Launching a named shell does not change the default. Refresh Shells is available within the submenu. Settings > Terminal offers Refresh Shells and Open Selected Shell. Refresh repeats installation checks rather than retaining the startup catalog forever.

Known installer locations and PATH provide automatic suggestions. Custom profiles extend the catalog with a name, executable and literal argument array. They persist with installation settings and are available to the same launch and default-selection paths as discovered shells. Adding a profile requires an executable resolvable on this installation. Missing custom executables remain listed for removal in Settings but are omitted from launch choices. Removing the selected profile releases the default preference.

Arguments use a JSON string array and are passed directly to the executable, without command-line concatenation or an intermediate shell. Profiles are limited to 32. Discovery does not execute candidate programs or classify arbitrary executables as shells. Automatic detection still recognizes known shell installers; profiles provide extension without hard-coded additions.

## Closing a Terminal

Paul decided on 28 October 2026 that closing a Terminal ends the shell and the programs still attached to its console, and that a windowed program started from the shell, such as Notepad or `code .`, goes on running. The question arose because closing a Terminal sometimes left its shell running. An earlier change that day ended a closed Terminal's shell and everything it had started, windowed programs included, through a job object for each shell; Paul narrowed it to this, and that job went. Each shell has a job of its own again for another reason, described below under Dinah's exit, and closing a Terminal does not end that job's processes.

Closing a Terminal closes its pseudoconsole. [ClosePseudoConsole](https://learn.microsoft.com/windows/console/closepseudoconsole) sends `CTRL_CLOSE_EVENT` to each client application "that is still connected", which lets an attached shell save its history and exit cleanly, and a program that does not exit on the event within the system's timeout is ended by the system ([HandlerRoutine](https://learn.microsoft.com/windows/console/handlerroutine)). A console program the shell is running, a dev server or `ping -t` for instance, is attached to the console and so ends with the Terminal. A windowed program is not attached to the console, nor is a console program that has left it with `FreeConsole` or was started with `DETACHED_PROCESS`, so neither receives the event and both go on running.

A shell closed in the moment after it starts may not have attached to its console yet, and then it misses the close event too. Dinah therefore waits up to 5 seconds (`pty.CloseGrace`) for the shell to end, and if the shell process itself is still running after that, ends it with [TerminateProcess](https://learn.microsoft.com/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess). That call ends that one process, and the page then receives `terminal:exit` as it does when the shell exits by itself. "Terminating a process does not cause child processes to be terminated", so nothing else the shell started is touched by it. When a shell exits by itself, Dinah closes its pseudoconsole in the same way, so a console program the shell left running in the background receives the close event as well.

The grace is counted from the moment of closing, not from when `ClosePseudoConsole` returns, because before Windows 11 24H2 that call may "wait indefinitely for the pseudoconsole to exit", and a shell that never attached could hold it until the shell is ended. The console is therefore closed on a goroutine of its own. `TerminalClose` returns at once and does the waiting off the page's path; closing a Terminal that is already closing does nothing more. When the window closes, every Terminal closes at the same time, so the window waits at most 5 seconds for all of them.

### Programs started from a Terminal and Dinah's exit

Paul decided later on 28 October 2026 that a program started from a Terminal that has left the console, a windowed program such as Notepad or `code .` or a console program started detached, keeps running after Dinah exits as well as after its Terminal closes. Until then every shell was inside Dinah's lifetime job, the job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` that ends everything Dinah started when Dinah exits, and so was everything a shell started, because a child of a process in a job is in that job from its creation ([AssignProcessToJobObject](https://learn.microsoft.com/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject)).

The first design gave each shell a job nested inside the lifetime job, with `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK`. It was not built, because the documentation does not settle what happens to the shell's children. [Nested Jobs](https://learn.microsoft.com/windows/win32/procthread/nested-jobs) says that a child "breaks away from the immediate job object and from each job in the parent job chain, moving up the hierarchy until it reaches a job that does not permit breakaway". The lifetime job has `JOB_OBJECT_LIMIT_BREAKAWAY_OK`, which [JOBOBJECT_BASIC_LIMIT_INFORMATION](https://learn.microsoft.com/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information) defines only for a child created with `CREATE_BREAKAWAY_FROM_JOB`, and a silent breakaway passes no such flag. Whether the lifetime job permits that breakaway is therefore not documented, and the children might have stayed in it.

What was built instead puts the shell outside the lifetime job, with each step documented:

1. Dinah's process joins its lifetime job, as before.
2. The shell is created suspended ([Process Creation Flags](https://learn.microsoft.com/windows/win32/procthread/process-creation-flags)) and with `CREATE_BREAKAWAY_FROM_JOB`, which the lifetime job's `BREAKAWAY_OK` allows, so the shell is not in the lifetime job.
3. While it is suspended, the shell is assigned to a new job of its own with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK`, and then it is resumed, so it starts nothing before it is in that job. [Job Objects](https://learn.microsoft.com/windows/win32/procthread/job-objects) describes this way of putting a child in a new job, creating it with `CREATE_BREAKAWAY_FROM_JOB` and then calling `AssignProcessToJobObject`.

The pseudoconsole is still given through the attribute list when the shell is created, and the restored Ctrl+C processing is inherited at creation too, so neither depends on when the shell is resumed.

With `SILENT_BREAKAWAY_OK`, "child processes of any parent process associated with the job are not associated with the job" ([Job Objects](https://learn.microsoft.com/windows/win32/procthread/job-objects)). The shell's job is not nested in the lifetime job, so the open question above does not arise, and everything the shell starts is in no job of Dinah's. The shell itself still ends with Dinah. Its job is created with no security attributes, so its handle "cannot be inherited" ([CreateJobObject](https://learn.microsoft.com/windows/win32/api/jobapi2/nf-jobapi2-createjobobjectw)), and Dinah holds the only handle. When Dinah's process ends, in any way, its handles are closed ([Terminating a Process](https://learn.microsoft.com/windows/win32/procthread/terminating-a-process)), and closing the last handle to a job with `KILL_ON_JOB_CLOSE` "terminates all associated processes", which is the shell alone. Agents and extensions are unchanged and stay in the lifetime job. A program the person approves for an extension to run in a Terminal is started the same way as a shell, since it runs in a Terminal too.

If the shell cannot be created with `CREATE_BREAKAWAY_FROM_JOB`, which happens when Dinah is in a job that does not allow breakaway, it is created again without the flag and in no job of its own. It is then inside the lifetime job as before, and so is everything it starts, which ends when Dinah exits. Dinah logs a warning saying so, once in a run.

On a normal exit the window closes every Terminal before Dinah's process ends, as described above, so a console program attached to a Terminal, such as a dev server, still receives the close event and ends. Windowed and detached programs keep running.

If Dinah crashes, it closes no Terminal. The shells end with their jobs, and their pseudoconsoles go away with Dinah's process. What Windows then does to a console program still attached to such a pseudoconsole is not documented, and Dinah does not rely on it. This is the accepted limit: after a crash, a console program started from a Terminal, such as a dev server, may keep running, and Dinah does not promise otherwise.

### Tests

A Terminal closed straight after it starts reports its shell's end, the close returns within a second, and closing twice does no harm. A `ping` the shell is running ends when the Terminal closes. A program the shell started that then left the console with `FreeConsole`, which stands in for a windowed program without showing a window, is still running after the Terminal has closed. In `internal/pty`, the shell is in its own job and not in the lifetime job, and such a detached child is in neither. Closing the shell's job, which is what Dinah's exit does, ends the shell and leaves the detached child running. A shell forced to start without breakaway is in the lifetime job with its child, and closing its Terminal still ends it.

Outside Windows Dinah has no pseudoconsole yet, and a Terminal there cannot start a shell. An implementation there keeps the same behaviour with POSIX means: the shell leads a session of its own with the pseudoterminal as its controlling terminal, closing the pseudoterminal hangs it up, which sends `SIGHUP` to the shell as the terminal's controlling process, the shell's end sends `SIGHUP` to the terminal's foreground process group, and `SIGKILL` follows to the shell alone after the same 5 seconds.
