# Chat recovery

Paul reported two Codex chats that could not reopen and an error notice naming Devin on 24 October 2026. He required access to their conversations even if the provider could not resume them, before work on image paste.

The pictured continuation had no messages of its own, but its complete local snapshot held 2,057 earlier entries. Its pending handoff and deterministic summary were intact. No provider rollout file was found for that thread ID. This is consistent with a thread created for a provider switch that had not received its first user turn before restart. The provider reported that its thread was not loaded. The precise provider persistence timing was not established and is not a recovery invariant.

OpenAI documents `thread/resume` as resuming a stored conversation by its ID and `thread/read` as reading stored metadata without loading the thread. See the [official app-server documentation](https://learn.chatgpt.com/docs/app-server). Dinah does not repair provider databases, invent thread IDs, or rely on parsing this particular error string.

## History access

Saved history is available independently of a successful provider connection. The saved view includes the continuation's parent snapshot and its own messages, including a continuation that has not received its first new message. Partial records remain readable and exportable with an explicit incomplete-history warning. Deleted records stay unavailable. A failed reconnect retains the saved view and the provider error. Error titles use the actual provider, inferred from the session ID when metadata has not arrived.

The failed-session notice offers Save History and Continue from Saved History. Saving exports the full local copy, including entries trimmed from the visible log. Partial history can be saved but cannot be presented as complete recovery context.

## Recovery

Recovery previews local history using the existing deterministic handoff budget, then creates a fresh provider session after the person confirms. It supports the same provider as the failed thread. The existing continuation implementation persists a parent link, complete snapshot, summary and pending handoff before switching the visible conversation. Original records remain unchanged. No model prompt is sent by recovery; the reviewed context accompanies the person's next message. Old links resolve to the recovered chat.

Recovery refuses a connected or reconnecting source, stale preview revisions, incomplete history, pending approvals and unfinished applet work. Recovery creation is serialized to prevent two attempts from creating competing children. The common continuation checks and rollback apply to both recovery and ordinary provider changes. Pending UI redraws transfer to the recovered session so replacing the thread does not discard unpainted history.

The Go tests check offline recovery of an unsent continuation, preservation of the original JSON, stale revisions, the recovered link and pending handoff, absence of model calls, and readable partial history. The browser recovery suite checks provider labeling, saved history, export, draft preservation and sending to the fresh thread ID. These tests use deterministic provider fixtures; they do not prove live provider availability.

## Saved Claude model missing on reopen

Paul reported on 28 October 2026 that Claude chats saved with the model "fable" sometimes refuse to reopen after a restart, with "this chat's saved model setting is no longer available from its provider". The log has eight such refusals that day, all for chats saved with "fable", and none for chats saved with "default" or "opus". Dinah raises the error itself when the saved value is not among the model option's values in the `session/load` response, because it will not silently move an existing conversation to another model.

The adapter (claude-agent-acp 0.87.0, and still 0.99.0) builds a session's model list once, when it creates or resumes the session, from the model list the Claude Code CLI returns at its initialize. It never rebuilds that list afterwards. Its later `config_option_update` notifications are sent only when the mode, the model or fast mode changes, and each one repeats the list the session started with. Waiting after the load for the agent to offer the saved value therefore cannot help, since this adapter never offers a value it left out at load.

Which Fable entry the CLI lists is not documented. Reading the CLI bundled with the adapter suggests that it adds the "fable" alias only when no other Fable entry is already in its list, and that a server-supplied set of extra model options, which the CLI refreshes in the background and caches in `~/.claude.json`, can supply one (on 28 October the cache held `claude-fable-5-1[1m]`, labelled "Fable", updated at 21:54, shortly before the 22:41 failure). Fresh sessions measured the same evening, including eight started at once, all offered "fable". The likely cause of the intermittent failure is that the CLI's list at startup depends on this cached server state, but that is undocumented behaviour, measured for understanding only, and no part of Dinah may depend on it.

No fix is built, because every route that would make these chats reopen by themselves rests on undocumented behaviour. Retrying the load until "fable" appears relies on the CLI's cache timing. Treating "fable" and `claude-fable-5-1[1m]` as the same model relies on an alias mapping the CLI does not document. Sending an unoffered value with `session/set_config_option` breaks the protocol, which allows only offered values. Two documented routes remain for Paul to choose between. The refusal could offer "Open with" one of the models the agent does offer, so the person picks the replacement and nothing changes silently. Separately, the adapter could be asked upstream to refresh a session's model list through the SDK's documented `supportedModels()` and announce it with `config_option_update`, after which a bounded wait in Dinah would become a documented fix.

### Decision: the person chooses the replacement (28 October 2026)

Paul asked for a better workaround than starting a new chat, and approved this one the same day. It applies to every option a chat restores, not only the model, because `restoreOptions` restores them all the same way. It is in `cmd/dinah-desktop/option_substitutions.go`.

When a reopened chat's saved value of an option is not among the values the agent offers, Dinah now sends those values to the page with the refusal. The bridge sends an error's detail beside its message when the error has one, and the page's promise is rejected with an `Error` that contains it. The error panel then offers Open With… beside Try Again, Continue from Saved History, Save History… and New Chat, and only for this refusal. Open With… lists each offered value with the name the agent gives it. A value whose name matches the saved value's name (from the provider's last catalog, where it is still listed) or the saved value itself, ignoring case, is listed first and marked Suggested; it is never chosen for the person. Choosing a value reopens the chat with it in place of the saved one, and the chat keeps it as its own choice from then on.

The panel also has a checkbox, "Always Use This When 'X' Isn't Offered". When the person ticks it, Dinah stores a substitution for the chat's provider in `settings.json`, under `optionSubstitutions`, as the option's ID, the saved value, the chosen value and the names shown. From then on, reopening any chat of that provider whose saved value is not offered uses the stored value without asking, when the agent offers it. The chat's saved value is kept, so the chat goes back to it once the agent offers it again, and a person choosing another value in the chat makes that one its own. Each time a substitution is used, the chat shows one line, such as "Opened with Fable (claude-fable-5-1[1m]) because Fable wasn't offered; you set this in Settings › Agents › Claude.", and the chat's log keeps it. When neither value is offered, the chat is refused with Open With… as before.

Settings › Agents lists each provider's substitutions under Saved Setting Substitutions, each with Remove, and leaves the list out when there are none. An entry in `settings.json` that is not a substitution (no option, a value no option can have, a value replaced by itself, or a second entry for the same option and saved value) is ignored, and a field of the wrong shape is ignored without stopping Dinah reading the rest of its settings.

Nothing maps one value to another by itself. Only the person's choice in the panel and the substitutions they stored apply, and a new chat's defaults are never substituted. No part of this depends on how the CLI chooses its list; it uses only the values the agent offers in its documented `session/load` response.

The Go tests check that a stored substitution is used when the saved value is missing and its value is offered, that the saved value is used when offered, that the chat is refused with the offered values when neither is, that the refusal lists the suggestion first, that Open With… makes the choice the chat's own and stores a substitution only when asked, Remove, and the settings round trip with hand-edited bad entries. The bridge test checks that an error's detail reaches the page. The browser suite `open-with` checks the panel, the suggestion's place, choosing a value, the checkbox, the Settings list with Remove, and the note in the chat.
