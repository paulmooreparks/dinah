# Decisions window

The Decisions window is a view of the engine contract in `docs/design/decisions.md`. It keeps the existing PUDL desktop shell. The interactive reference remains provisional, so the master-detail layout is confined to a separate stylesheet and applet module. The Architectural Principles are at `C:\Users\paul\OneDrive\Documents\Architectural Principles.md`.

The window opens maximized. A narrow window uses the same master-detail content one region at a time, with Requests returning to the list. These choices are confined to the applet registration and stylesheet. The request list occupies a fixed scrolling region. New identities append in stable arrival order, with a fixed row height and no automatic selection or focus change. The detail region keeps its selection while the list refreshes. Numbered questions show the original wording, recommendation, optional choices and a separate answer input. As Recommended fills an explicit draft answer; only Send submits it. The explicit canDismiss field controls dismissal for plain mentions and orphaned structured requests; its explanation remains visible. Plain mentions have their original first line and a reply field without an invented recommendation. The engine supplies destination identity and display text, which remain visible beside Send.

Selection and text filtering use the workbench view address. Drafts are keyed by durable request identity in the existing saved UI state, with answer text, recommendation selection and the reviewed request content. They survive closing and reopening the applet and reloading the window. Storage failures remain visible and cannot be called saved. An incoming request update does not replace focused text. Changed question or destination content requires review before submission. Partial answers leave unrelated drafts intact.

Before submission, the page saves its operation identity and immutable payload. A lost or invalid receipt remains unconfirmed and blocks another send until the engine can reconcile it. The page never infers failure from a timeout or sends a corrected mutation until its earlier attempt has a terminal receipt. On an unknown receipt, it retries only the identical call, as the engine contract requires. The exact request, answer and broadcast method shapes come from Engine's contract rather than being invented by this view.

Broadcast to Active and Broadcast to All are separate commands. A command opens an addressable compose view, obtains an engine preview, and shows its count and complete title list before asking for confirmation. Editing its text invalidates that preview. Each scope keeps a separate saved composition and preview, so switching scopes cannot reuse the other scope's token. Cancellation sends nothing. Sending uses the engine's preview identity and background admission policy; the page does not open recipient windows.

Verification uses only affected headless suites with synthetic engine responses and saved UI state. It covers empty, unavailable and failed reads; structured and plain requests; partial answers; draft reload and write failures; changed content; uncertain delivery and reconciliation; broadcast preview, cancellation and confirmation; address navigation and fixed geometry on arrival. Native notifications, installed programs and real bus recipients are outside these browser fixtures.

A saved request snapshot keeps its destination and questions available for receipt recovery even after the row has closed and disappeared from the open list. Saved operations admit only the three declared mutation methods and remain bound to their request or broadcast identity. An invalid saved record is shown as an error and preserved. The page does not execute or replace it.

Refresh rereads the number of pages already loaded and continues through earlier pages until it finds the selected open row or reaches the end. This also supports a notification link to an older request. A request absent from the complete read remains visible from its saved snapshot, with sending disabled. The page does not infer closure from absence in a single page.

The status bar reserves the width of its Decisions count, including its loading and unavailable states. Its accessible label keeps the full count when the badge shows 99+. DecisionEntries returns a complete identity index using the engine's existing open-row predicate. It contains only the count, opaque request identities and source message numbers. One shared, coalesced read supplies the count and notification navigation; a bus change invalidates an in-flight snapshot, and a failed read shows an unavailable count rather than zero.

Structured requests already reach the durable attention watcher through their human-addressed bus messages. The page reuses those grouped cards. A card resolves its message against the current index before opening Decisions, and clears only the captured notification identities after its requested row has been read and shown. Lookup, row-read and navigation failures retain the card. A later request from the same chat survives an earlier card's navigation. Messages outside Decisions keep their existing source-chat or group navigation. Opening a request clears its attention card without answering or dismissing the durable decision. These entry points do not alter the Decisions window layout.
