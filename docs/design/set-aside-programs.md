# Removing set-aside programs

The person may remove selected older installed programs from Settings. Nothing removes them automatically. The service owns the product home bin directory and derives its program names from the profile's CommandProgram, WindowProgram, ToolServers and ProgramCommands. It accepts no caller paths. A distribution's existing profile therefore covers its additional programs without product names in the host.

## Window contract

`ListSetAsidePrograms() -> {items: SetAsideProgram[], totalBytes: number, warnings: string[]}` is a page query. Each item has `id`, `program`, `name`, `sizeBytes`, `date` (UTC RFC3339), `runningPids` (always an array), `fallback`, `canRemove`, `reasonCode`, and `reason`. `date` is the set-aside timestamp encoded by the installer, rather than the original executable's modification time. The list is ordered by program then descending date then name.

`RemoveSetAsidePrograms({ids: string[]}) -> {items: RemovalResult[], removedBytes: number}` is page work. Each result has `id`, `state` (`removed` or `refused`), `reasonCode`, and `reason`. The input contains 1 to 100 unique 64-character hexadecimal IDs. Malformed input fails before changes. Individual refusals allow other selected eligible files to be removed. A changed or missing ID returns `changed_or_missing`; other refusal codes are `in_use`, `fallback`, `unrecognized_date`, `unsupported`, and `io_error`. The page refreshes after settlement. After a lost response it lists again; retrying the same IDs cannot select replacement files.

IDs are opaque SHA-256 selections bound to the absolute bin directory, basename, file identity, size and modification time. The service reconstructs the current list and matches IDs; it never interprets them as paths. There is no expiry or hidden selection state. A changed file needs a fresh selection and confirmation. Displayed bytes are logical file lengths, not a promise of physical disk recovery where hard links or filesystem compression exist.

The Go API in internal/programs is `NewSetAsideService(bin string, programNames []string) *SetAsideService`, `(*SetAsideService).List() (SetAsideList, error)` and `(*SetAsideService).Remove(RemoveSetAsideInput) (RemoveSetAsideResult, error)`. Program names have no extension, as in the product profile. `SetAsideList.Items` is `[]SetAsideProgram`; `RemoveSetAsideInput.IDs` is `[]string`; `RemoveSetAsideResult.Items` is `[]RemovalResult`. DTO fields use ordinary exported Go spelling (`ID`, `Program`, `Name`, `SizeBytes`, `Date`, `RunningPids`, `Fallback`, `CanRemove`, `ReasonCode`, `Reason`, `TotalBytes`, `Warnings`, `State`, `RemovedBytes`) with the JSON spellings above. Date is a string and PIDs are uint32 values.

## Protection and ordering

Only regular, non-reparse files named `<profile program filename>.old-<timestamp>[-suffix]` are candidates. Both the earlier 17-digit UTC calendar timestamp and Unix nanoseconds are recognized. A malformed timestamp is listed with its modification date and refused. The highest recognized timestamp for each program is the fallback. Every copy tied at that timestamp is protected. An unrecognized timestamp also blocks removal of that program's copies because its newest fallback cannot be established.

Earlier manual copies named `<profile program filename>.before-<label>-<yyyymmdd>-<hhmmss>` are also listed, with the trailing calendar date interpreted as UTC. Their label must be nonempty. Recognized .old copies take fallback precedence over every .before copy, regardless of date. When no .old copy exists, the newest recognized .before date is protected, including ties. Malformed dates under either recognized prefix are listed and refused; other names stay invisible. Tests include both patterns side by side.

On Windows, process discovery enumerates loaded modules and asks GetMappedFileName for the file mapped at each module address, opens that file, and compares volume/file identity with each candidate. It does not assume any module order. A copy mapped as a library is also protected. GetProcessImageFileName is unsuitable here: a hidden rename regression showed it reporting the old pathname and therefore identifying a replacement image incorrectly. Basenames do not identify a running copy.

The listing reports processes that could not be inspected in warnings. Module enumeration, mapped-name lookup and file opening form a snapshot, with ordinary exit, rename and load races; shared mapped paths are cached within that snapshot. This cannot prove that an unmarked file is unused. Removal takes a fresh process snapshot at the start of the confirmed batch, opens each selected file with DELETE access, checks its identity again, holds it against replacement, refreshes fallback selection, and requests ordinary FileDispositionInfo deletion on that handle. It never uses POSIX deletion or bypasses mapped-image protection. Windows rejects ordinary deletion of a mapped executable, including a process started after inspection. Failure is a refusal and preserves the file. Other platforms refuse removal until they have an equivalent documented implementation.

The implementation uses [EnumProcessModulesEx](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-enumprocessmodulesex), [GetMappedFileName](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-getmappedfilenamew), [FILE_ID_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info), [CreateFile sharing rules](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), and [SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle). The [DeleteFile contract](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-deletefile) documents the refusal for memory-mapped files. Device names are opened through the documented [GLOBALROOT namespace](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file). The service does not delete by a path after its identity check.

## Ownership and verification

Engine owns internal/programs service and platform files, the App methods in a new set_aside_programs.go file, and their pageMethods rows. Front End owns Settings and any Updates presentation. Quality may construct `programs.NewSetAsideService(tempBin, []string{"window", "command", "tools"})`, use real executable filenames with programs.FileName, and call List and Remove directly. Tests use invented files with recognized timestamp suffixes and controlled modification times. A hidden pipe-driven child proves running-image identity, including a renamed executable, and protection if it starts after listing. Tests also cover hard-link identity, identical basenames in different directories, fallback ties, replacements, invalid selections, and removal of only selected eligible files. No real home or desktop input is needed.
