# Dinah Design

## Status

This document records the design of Dinah as Paul Parks and Claude have worked it out since 21 October 2026, and every decision in it is Paul's unless it is marked as a recommendation. Dinah was called Studio while it was being designed, and the name changed on 22 October 2026. Paul uses Dinah for his own work as early as possible, so the delivery plan at the end starts with pieces he can use within days.

Paul's cross-project Architectural Principles, the DIRT principle and the rule against relying on undocumented behavior apply to Dinah as they do to Paul's other projects. This document refers to them and does not restate them; the two exceptions Dinah makes to them, the browser-drawn shell and Devin's model prices, are recorded below.

## Exit confirmation

The [exit-confirmation design](docs/design/exit-confirmation.md) records interruption checks and the Cancel-first close handshake. Active chats and work without automatic recovery require explicit confirmation before layout saving and shutdown.

## Native full-screen mode

The [native full-screen design](docs/design/native-fullscreen.md) defines F11 and View > Full Screen, native placement restoration and PUDL application-window controls. Native mode remains separate from maximized content windows and browser fullscreen.

## UI responsiveness

The [UI responsiveness design](docs/design/ui-responsiveness.md) records the scheduling contract, implemented boundaries and remaining migration work. Provider output and history reconstruction yield between bounded batches. Optional timing diagnostics measure stalls and input delay; an FPS display is not planned.

## Fonts and themes

The [fonts and themes implementation](docs/design/appearance.md) provides Mineral as the default and Linen as the alternative, with global font roles, personal content overrides, a workbench Theme Editor and versioned Dinah theme import/export. PUDL controls Light, Dark and System mode. Document surfaces follow appearance while embedded artwork retains its colors.

## Approve Everything for Codex and Ollama

Settings > Agents offers Approve Everything (`all`) for Codex and Ollama, as requested on 24 October 2026. It allows shell commands, writes outside the workspace and bundled applet actions without a permission question. The existing Codex sandbox choices and Ollama's Once in Each Chat, Every Command and Never choices remain compatible with saved settings. Approve Everything overrides the Codex sandbox choice with full access.

Saving the choice updates open provider sessions. Ollama uses it from the next turn. Codex applies host consent immediately and sends the sandbox and approval policy with its next `turn/start`, using the documented [TurnStartParams overrides](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/v2/TurnStartParams.ts). New and resumed Codex threads use `danger-full-access` and `never`. Managed applet connection configuration is also updated when a thread opens or resumes.

The Settings applet cannot read or change these approval preferences. Protected settings files remain refused by the host's file-write handler. Both providers refuse recognized direct CLI `credential` and `flow answer` commands before granting command approval. The command guard covers Dinah's CLI names, including quoted executable paths; it does not parse arbitrary shell programs or restrict commands that Codex runs without asking the host. Human questions still require the person's answer.

## Files per Message

Each provider's card in Settings › Agents has Files per Message, the most files the person can attach to one message in a chat of that provider (Paul, 28 October 2026). The Agent Client Protocol has no field by which an agent reports such a limit, so the limit is a setting, and its default comes from the provider's documentation, which the card quotes beside the field with a link to the page. Save sets another number, an empty field means no limit, and Use Default returns to the documented default. The files counted are those pasted, dropped or attached from the computer; a document chosen from a workspace goes as a link and is not counted.

| Provider | Default | Source |
| --- | --- | --- |
| Claude | 20 | Anthropic's [vision guide](https://platform.claude.com/docs/en/build-with-claude/vision) allows 600 images in one API request, and 100 for models with a 200k-token context window. Above 20 images in one request, any image over 2000 px on a side is refused, and images sent in earlier turns count toward the 20. |
| Codex | 20 | OpenAI's [images and vision guide](https://developers.openai.com/api/docs/guides/images-vision) documents a ceiling of 1,500 images and 512 MB in one request. Paul chose 20, below that ceiling. |
| Devin | No limit | Devin's documentation gives none. |
| Ollama | No limit | Ollama's API documentation gives none. |

A number above the documented ceiling is refused, since the provider would refuse the message. With no limit Dinah sends what the person attaches and shows the provider's error if it refuses a file.

At the limit, a chat's box refuses a further pasted or dropped file with the reason and the setting's place, the line under the chips says no more files can be attached, and Add › Files From This Computer… is disabled with the reason as its tip. A group's box does the same with Attach…, using the smallest limit among its member chats that have one and saying which member set it; the plan for the person's attachments in groups ([group-attachments.md](docs/plans/group-attachments.md)) records how delivery honours each member's own limit. Go checks the count again when a message is sent, so a message over the limit never reaches an agent.

Because a long Claude chat passes 20 pictures sooner or later, Dinah reduces any picture whose longer side is over 2000 px to 2000 px before a Claude chat is given it, keeping its proportions and its format. PNG, JPEG and GIF are rewritten with the standard library's documented encoders, and every frame of an animated GIF keeps its palette. Go has a documented WebP decoder (`golang.org/x/image/webp`) and no WebP encoder, so a WebP picture over the size is sent as it is, and the prompt tells the agent so. Other providers receive pictures unchanged.

## Devin Model Prices

Dinah shows what each Devin model costs in the model list, under the model's name, and in a Devin chat's Usage panel (Paul, 28 October 2026). The Agent Client Protocol gives a model a value, a name and a description, and the model options `devin acp` sends contain no price. Devin's command line prints prices with `devin models list --format json`. Devin's [command reference](https://docs.devin.ai/cli/reference/commands) documents that command and describes `--format json` as machine-readable output for scripts, but it does not document the fields of that output.

**An exception to the rule against relying on undocumented behaviour.** Paul approved relying on those undocumented field names on 28 October 2026, on the condition that every way the dependency can break leaves Dinah as it was before prices existed. Dinah reads these fields, as Devin 3000.4.25 printed them: `families`, each family's `variants`, and in each variant `model_uid`, `cost_summary` (such as "$4 / MTok In · $20 / MTok Out"), `cost_tier` (such as "High cost") and `max_context_tokens`. It also relies on one undocumented equality, that a variant's `model_uid` is the value `devin acp` gives the same model in its model option. On 28 October 2026 all 82 models `devin acp` offered on Paul's machine matched a `model_uid` exactly; Devin documents no mapping between the two, so Dinah matches on exact equality and nothing looser, and a model that does not match gets no price.

Dinah runs the command with the Devin executable it already uses, with no window and an eight-second limit, in the background, so nothing waits for it. It runs once when Devin starts, again when Devin starts as another executable or version, and again when the person opens the model list or the Usage panel an hour or more after the last read. Only a field of the expected type is used: `model_uid` and `cost_summary` must be non-empty strings for a model to get a price, `cost_tier` must be a string and `max_context_tokens` a positive whole number, and anything else is ignored.

When the command is missing, fails, runs past its limit, prints more than 4 MB, or prints something that is not this shape, Dinah has no prices. The same is true for a model whose fields are missing or of another type, or whose value matches no `model_uid`. With no price, a model's row is drawn exactly as before and the Usage panel has no Model Price section, so nothing is broken and nothing wrong is shown. The failure is written to Dinah's log as information, and Settings › Agents › Devin says that prices come from the Devin command line and may be missing if Devin changes what it prints.

## Why Dinah Exists

On a typical day Paul has five Visual Studio Code windows open, each on a different workspace, several of them holding more than one repository, and each running one or more Claude Code sessions. The agents in those windows cannot talk to each other, so Paul carries every message between them by hand. When a consuming project needs a change in PUDL, its agent writes a proposal in its own workspace, and Paul copies the proposal's path into the PUDL agent's chat. When a library that four other workspaces use cuts a release, Paul visits each window in turn to say so and to ask whether it is ready to upgrade. He is drowning in copy and paste and in shared Markdown files.

A second reason is that ideas arrive faster than Paul can act on them, and AI has made that worse rather than better: the more he produces, the more new possibilities he sees. He needs somewhere to hang ideas as fast as they arrive, wherever he is, and a way to start experiments on them without disturbing the work already running.

Dinah is the place where all of this happens in one application. It is a content-production studio in which working code is one kind of content among several, and most of what Paul creates and edits is Markdown. Dinah is not a code IDE, and it will not be built as a fork of Visual Studio Code. Paul finds forks just different enough from VS Code, or just far enough behind it, to add friction, and their one-workspace-per-window architecture works against everything that makes Dinah worth building.

## What Dinah Draws On

Dinah's shell is a workbench of PUDL applets with a terminal, a file browser, an editor and a virtual file system, in which AI chat is an applet that can drive the whole application. parkscomputing.com is built the same way, and Dinah takes its Terminal applet and its designs where they help. Dinah also draws on these:

- Andoneer, for budget pacing, model-tier-aware pulling, unattended runs and the pending-decisions view.
- The board tool formerly named Dinah, for what its storage design and its served column instructions taught; none of its code comes across.
- parkscomputing.com's [GitHub mount design](../paulmooreparks/parkscomputing/Architecture/github-mount-design.md), for mounting repositories without cloning them.
- PUDL, for every pixel of the interface.

## Portfolio, Instances and Workspaces

A Dinah instance is one running daemon with its own state folder, and it holds a portfolio of workspaces. Paul runs several instances rather than one that holds everything; the obvious split is his personal work on one machine and his employer's work on his work laptop. Within an instance, the goal is to let Paul create at the speed his mind runs.

A workspace is a named set of folders, usually one or more repositories, as a VS Code workspace is. Each workspace has its own agents, its own board and its own files. The workspace is the unit of trust described below.

Instances can subscribe to each other. The work instance must still receive new PUDL builds, and its proposals back to PUDL are valuable, so it cannot be cut off from the rest of the herd. A subscription passes release notices and proposals between instances and nothing else.

## Agents and Providers

Dinah runs agents from several providers in one place. Each provider is reached through its documented interface:

| Provider | Route |
| --- | --- |
| Claude | The Claude Agent ACP adapter, which uses the official Agent SDK. Each person uses their own Claude Code sign-in or a Claude Console API key, and Dinah never offers a Claude login of its own. |
| Codex | The documented Codex app-server protocol. |
| Devin | ACP, through `devin acp`. |
| Ollama | Ollama's documented native HTTP API, with Dinah supplying the tool loop and conversation storage that Ollama lacks. |
| Gemini and others | Added as Paul gets to them. Any agent that speaks ACP is the cheapest to add. |

Claude Code is Paul's favourite agent, and the arrangement above lets him use it on his Max subscription. Anthropic's help article, updated 7 October 2026, permits the Agent SDK and third-party apps to use a person's own subscription limits, and the SDK falls back to the person's own Claude Code login when no API key is set. If Anthropic changes its position again, interactive `claude` running in Dinah's terminal always draws on the subscription, and Claude Code's documented channels can carry Dinah's messages into such a session. Channels are a research preview, so that route is a fallback.

Every chat keeps its own provider session. A turn an agent takes in a room or in answer to another agent runs in that agent's real session, so what it learns stays in its memory when Paul returns to its own window.

## Messaging Between Agents

Every agent session has an inbox. Asking another chat a question, speaking in a shared room, sending a document and announcing a release are all different ways of addressing inboxes, and they share one delivery mechanism, the bus. A question one chat asks another with `dinah.chat/ask@2` has been a bus message since 28 October 2026: it goes from the asking chat's session to the asked chat's, so it opens a closed chat as any message to that chat does, and the answer comes back to the asking chat as a completion report on the bus (docs/design/chat-messaging.md).

Delivery depends on whether the receiving agent accepts messages while it is working. A steerable agent receives a message in the middle of its turn. An agent that is not steerable, which today includes Devin, receives its queued messages at its next turn boundary, with a header saying what it missed. Paul and any steerable agents never wait for the slow participant.

### Shared Rooms

A room holds Paul and two or more agents, possibly from different workspaces. The motivating case is a PUDL proposal, where Paul, the agent that wrote it and PUDL's agent hash out the details together. An agent Paul mentions answers, an agent another agent mentions answers next. A group has no limit on these handoffs unless Paul sets a turn budget for it, and when the budget is spent the mentions still arrive but start no turns until Paul posts. One rule is open: when Paul speaks without mentioning anyone, either every agent answers in roster order or, as Claude suggested for a design discussion, only the agent being addressed answers.

### Proposals Between Workspaces

A proposal is a document one workspace sends to another to ask for a change. The PUDL loop works like this:

1. The consuming workspace's agent writes the proposal in its own workspace and sends it to PUDL's inbox. The message contains a live link to the file, together with the commit or content hash of the version sent. The link gives PUDL's agent read access to that one file and nothing else.
2. The proposal becomes a card in the intake column of PUDL's board, with a link to the document and the workspace it came from.
3. Paul opens a room from the card with both agents, and either agent may revise the proposal while they talk.
4. PUDL's agent implements the change only after Paul approves it. The proposing workspace can file into PUDL's intake, and only PUDL's own agent writes PUDL's code.
5. When PUDL releases, the release notice described below reaches every workspace that depends on it, and the workspace that asked for the feature also receives a direct message saying its proposal shipped.

The receiving workspace writes its own document from the proposal, copying whatever parts it wants and adding its own decisions. The receiving document records the proposal's path and the hash it was drafted from. When the proposal changes after that, Dinah flags the difference so that someone can decide whether it matters, and nothing drifts silently. Links therefore point at files in git-tracked workspaces, where "the version it was drafted from" has a stable answer.

### Release Notices

Each workspace records which other workspaces it depends on. When a library's agent cuts a release, it sends a release notice containing the version, the changelog and any breaking changes to every dependent workspace. Each dependent agent checks the notice against its own repository and replies with one of three verdicts:

- Upgrade now.
- Sit this cycle out, with a reason and a date to ask again.
- Blocked until the library changes, which also files a card on the library's board.

Paul sees one tally instead of visiting every window, and each verdict becomes a card on the consuming workspace's board. The thread stays open for discussion.

Upgrades and proposals are the same cycle seen from opposite ends. Proposals travel upstream to the library, releases travel downstream to its consumers, and the boards track both.

## Trust Between Workspaces

Workspaces trust nothing by default. Paul can grant one workspace access to another, which he does from time to time today. A grant goes in one direction and records four things:

- The workspace receiving access.
- The workspace or folder it covers.
- The level, which is read, write or running commands.
- How long it lasts, either until Paul revokes it or until a particular card is finished.

Dinah enforces grants itself and never relies on an agent's instructions to stay within bounds. For a read grant, Dinah's daemon offers the granted files to the receiving agent as its own MCP tools and checks the grant on every call, which works the same for every provider. A write grant configures the provider's own documented sandbox, such as Claude Code's permission rules or Codex's writable roots. A provider that cannot enforce a write grant through a documented mechanism is never offered one.

Every grant appears on the portfolio view, each workspace lists who can see into it, and every read or write made under a grant is logged in the granting workspace.

Access and authority are separate questions. A grant says whether an agent can reach another workspace. Whether an agent may act on another agent's request is decided separately, by Paul's approval or by a link he has marked as trusted. Sending a document with a proposal needs no grant at all, because the attachment gives access to that one file only.

## Boards

Dinah tracks tasks itself. Every workspace has one board, kept under Dinah's state folder and created by its first task, which the command line drives as `dinah task` and Dinah Desktop shows in its Tasks and Task windows. Paul decided on 25 October 2026 that this is a new, lighter feature of Dinah and not a merger with his old board tool, and that no old boards are imported. The design is in [docs/design/task-tracking.md](docs/design/task-tracking.md). A program board across instances, which would give Paul the cross-project view a program manager needs, waits until the per-workspace board is in use.

From Andoneer, Dinah takes policies rather than code: budget pacing against Paul's Claude Max limits, pulling work according to model tier, unattended overnight runs, and the pending-decisions view, which becomes Dinah's main screen.

## Ideas and Experiments

### Capturing Ideas

Ideas reach Paul everywhere: at his desk, walking, driving, running, lifting, in the shower, in meetings, at dinner, watching television and in bed. Capture therefore cannot be a feature of the desktop application, which may be asleep or on another machine. It is a small hosted inbox that only Paul can post to, and each instance collects from it while it runs. A Tela service would fit the job.

The inbox has two front doors:

- A system-wide hotkey on the desktop opens a capture box over whatever Paul is doing, and Enter returns him to where he was.
- A capture page on the phone, installed as an app, in the same way Paul already installs parkscomputing.com, its Sudoku applet and yavchn.com. It accepts typed text, a photo or the phone's own dictation, and it queues captures while the phone is offline.

Capture asks for nothing except the idea itself. Paul does not choose a project, a tag or a priority, because making that decision on the spot is the friction that loses ideas. The capture records what Paul was doing when it came from the desktop, such as the workspace and the document or chat in front of him, so that the idea still makes sense weeks later. Audio is kept alongside its transcript, because dictation mangles names like PUDL and Dinah.

### What Happens to an Idea

An agent files each captured idea into the instance's idea board, and Paul corrects the filing when he reviews it. The agent also compares the new idea with existing ones and links them. An idea Paul keeps having is telling him something, so how often an idea recurs becomes a signal of its importance, and duplicates merge instead of piling up. On request, a background agent can turn an idea into a short write-up of what it is, what it would touch and what already exists that it could reuse, without interrupting Paul's current work.

Paul reviews ideas when he chooses to, in a view that shows clusters of related ideas and the write-ups that have grown. The view shows no unread count and sends no reminders.

An idea about work captured on Paul's personal phone lands in his personal inbox, and the filing agent forwards it to the work instance. If his employer's policy forbids work content on personal infrastructure, work ideas need a front door of their own.

### Experiments

An experiment is a workspace with its own folder, its own agent and a small board. Starting a new experiment scaffolds all of these. Forking an existing project creates a git worktree on a new branch, or a clone when Paul wants it fully separate, so the original project's folder, branch and agent are never disturbed.

An experiment is running, parked, promoted or discarded. If ideas outpace Paul's attention, most experiments spend most of their lives parked, so parking costs nothing and loses nothing. When Paul parks an experiment, its agent writes a note saying where it got to and what the next step is, and resuming starts from that note rather than from a cold session. Promoting a fork either merges it back or turns it into a project of its own.

Dinah does not limit how many experiments run at once. Paul was unsure whether a limit would help or become something to fight, so Dinah starts by making the number visible. It shows how many experiments are active and how long since anyone touched each one, and an experiment untouched for a set time moves to a "gone quiet" group where it can be parked with one click. After a few weeks of real numbers, Paul can turn on a soft limit, which only changes a colour, or a firm one, which asks which experiment to park when he starts another.

### What Needs Paul

Paul's attention is the scarce resource, so Dinah's main view shows what is waiting for him: agents waiting on a decision, rooms waiting for his reply, proposals waiting for approval and verdicts that need a ruling. Everything else runs without him. The view also shows time and budget per experiment, because Paul does not feel time passing on work he is not looking at.

## Documents and Files

Most of what Paul makes is Markdown, so the Markdown editor is the centre of Dinah. It is a WYSIWYG view of a document alongside a source view, and Dinah also has a diff view for reviews.

The Editor has a diff view, built on CodeMirror's merge view (`@codemirror/merge`, vendored with the rest of CodeMirror) and themed from PUDL's tokens as the Editor's text is. `window.dinahDiff.open(spec)` opens a Diff window, or brings the window with the same key to the front with new texts, and the window shows the two texts inline or side by side with line numbers, a sign column, a sticky strip above each hunk and tick boxes on changed lines. Whoever opens a diff hands it the actions to show for the file, for a hunk and for ticked lines, and each press comes back to the opener with the hunk and the lines it applies to, so one viewer serves Git, reviews and agents' suggestions (Paul's decision of 25 October 2026, recorded in dinah-git's `docs/design/overhaul.md`).

Checklists are editable lists in Visual view. Insert > Checklist, the formatting toolbar's Checklist command and `/checklist` on an empty line create an unchecked item with its placeholder selected. Enter continues the checklist with an unchecked item. Checkbox clicks and Space update the Markdown through undoable transactions. The document loader recognizes the preview's `tasklist` classification as rich content, including lists written with `*`, so an existing checklist opens directly for editing. Unchanged source formatting is preserved, and checking an item changes only that item.

The Visual view gets its own choice of light or dark, apart from Dinah's theme (an idea of 23 October 2026, not yet planned). Paul usually wants it to follow the dark theme, but sometimes he wants a light page in a dark window, because it shows how a document will look on paper or in a system that has only a light mode. Paul's editors and file browsers have drifted apart across his projects; one version of each, in a shared package all of them use, would stop that, and Paul's `pudl-applet-packages` repository may be the right home for it.

### The Virtual File System

Dinah presents a Linux-like file tree that covers more than the local disk, with each workspace at `/workspaces/<name>` and Paul's own space at `/home`. Mounts can include:

- Local folders, which are the only kind today.
- Git repositories, mounted for browsing without a clone, following parkscomputing.com's GitHub mount design, which reads GitHub's tree and contents APIs and caches each file by its blob hash.
- Cloud drives: Dropbox, Google Drive, SharePoint and OneDrive, each mounted as a folder of a workspace through the drive's own documented API (an idea of 23 October 2026, not yet planned). The workspace's agents read and search them through the daemon's MCP tools, as they reach any mounted source.
- Other web sources.

Paul can still reach the local file system directly to upload and download.

The file system serves two audiences. Paul reaches it through Files and the editors. Agents such as Claude Code and Codex work on real files on disk and cannot see a virtual mount, so they reach mounted sources through the daemon's MCP tools, as they reach other workspaces under a read grant. When an agent needs to build, run tests or commit, it works in a real worktree, because those tools need real files. Dinah does not use an operating-system-level virtual file system.

## Applets

Dinah is a shell with applets, and AI chat is just another applet. Every applet offers typed actions, so an agent's tools are the sum of what the installed applets offer, and installing an applet gives every agent new abilities. Applets can see and call each other.

Applets Dinah does not ship are extensions, and Paul decided on 23 October 2026 that new features come as extensions rather than being built into core Dinah, which may later shed what it has built in. An extension is installed from a folder or a zip, runs its back end as its own MCP server process and its front end in a sandboxed frame, and reaches Dinah only through a published contract of host tools and contributions: panes, commands, decorations on files and lines, workspace groups and actions. The Git applet is the first, built in its own repository in Go against the contract alone, and it does everything by running real `git` commands, each shown in a Command Log with Run in Terminal so that Paul learns the command line as he uses it. The design is in [docs/plans/extensions.md](docs/plans/extensions.md).

Agents keep working when no window is open, so an applet cannot exist only inside a web page. Each applet has two parts:

- A back end that offers the applet's actions and runs in the daemon whether or not a window is open.
- A PUDL front end that draws the applet when Paul is looking. An action that only makes sense with a window, such as opening a file in a split, reports an error when no view is attached.

An applet's back end runs in one of two ways:

- As a separate process that speaks MCP. It can be written in any language, including native code, and a crash cannot take the daemon down. Any existing MCP server becomes an applet without a user interface, and Dinah's applets can serve agents outside Dinah too.
- As WebAssembly inside the daemon through wazero, which is pure Go and suits applets that should be sandboxed.

Dinah does not use Go's `plugin` package, which does not run on Windows and requires plugins built with the host's exact Go version.

An action's result has two parts, as an MCP tool's result does. The output is a JSON object checked against the action's output schema, for programs and for agents that read fields. The text is optional Markdown written for a person or an agent to read, the counterpart of MCP's `content` beside `structuredContent` (`contract.Result.Text`). An action should give text whenever its result is something to read, because wherever Dinah shows a result to a reader, in a chat's completion report or a chat's history, it shows that text, and it never interprets an action's output to make one. The broker keeps the text in the saved invocation beside the output. An action that gives no text is shown as a line with the request and its status, any error, and then its output as an indented JSON block. A bundled applet sets the text in its handler; dinah.chat/ask@2 writes which chat answered and the reply as that chat wrote it. An extension's text is the text content of its MCP tool result. The SDKs repeat the structured result there as JSON for older clients, as the MCP specification recommends, so a block that is only that JSON is left out.

Applets have to be rich enough to be whole editors, and they may come from contributors other than Paul (an idea of 23 October 2026, not yet planned). An extension could add an editor for Google Docs, or for Word, Excel and PowerPoint files, and open those files from Files and the mounted drives the way the Markdown editor opens Markdown. The contract therefore has to cover an applet that owns a document's whole window, its menus and its saving, and installing an applet from someone else has to show what it may reach before it is allowed to.

One applet Dinah ships itself is a log reader (an idea of 23 October 2026, not yet planned). It opens and follows logs of several kinds, docks them beside the windows that write them, and has a language server that understands each kind, so a log has the same hover, outline and error marks as code. Agents reach the logs through the applet's actions, so a chat can read the log of the run it is debugging.

Paul's applet hosts need one applet contract, or shared packages drift as soon as they are extracted. parkscomputing.com's PUDL proposals for applet hosts, actions and handlers are the starting point. If Dinah takes off, a plugin studio follows almost for free, because building an applet is just another kind of project to run in it.

## The Interface Is PUDL

PUDL is the only interface Dinah has. Paul enjoys using and looking at it to the point that he finds other interfaces abhorrent, so this is a rule rather than a preference, and it has three consequences:

- Borrowed components, such as CodeMirror's completion lists, tooltips and gutters and the xterm.js terminal, are themed from PUDL's tokens so that nothing in the window looks foreign. Where a component cannot be themed far enough, the gap becomes a PUDL proposal.
- An applet's front end is built from PUDL components and nothing else. Dinah checks this when an applet is installed rather than leaving it to code review.
- Dinah becomes PUDL's main consumer. PUDL is one of the workspaces open inside Dinah, Dinah's needs reach PUDL as proposals, and PUDL's releases reach Dinah as release notices, so the loop Dinah implements is tested by Dinah's own development.

## Editors and Languages

Code editing is incidental in Dinah, and its problem is breadth rather than depth. Paul wants to support new languages as quickly as possible and let their quality improve over time. Dinah's editor is built on CodeMirror 6, which suits this well:

- CodeMirror's author publishes `@codemirror/lsp-client` under the MIT licence. It provides completion, hover, signature hints, go-to-definition, rename, formatting and find-references, and the host supplies its transport. In Dinah the browser talks to the daemon over a WebSocket and the daemon runs each language server over standard input and output, which works the same on the desktop, the web and the phone. The author says the package has not seen much use yet.
- The mason registry, built for Neovim, lists hundreds of language servers, linters and formatters, and each entry says where to download the server and which executables it provides. Dinah reads the registry and installs a server the first time Paul opens a file in its language.
- CodeMirror's language data provides syntax highlighting for many more languages before any server is installed.

A language server running in the daemon can also be offered to agents as a tool, which would give Ollama models go-to-definition and find-references.

What the language servers report is shown wherever code appears, not only in the Editor's own completion and hover (an idea of 23 October 2026, not yet planned). Errors and warnings mark the Editor's gutter and collect in a Problems view across the workspace, hover and outline information is available in Files and previews, and the same diagnostics are offered to the workspace's agents, so a chat can see what is broken without running the build.

## Architecture and Stack

Dinah is built daemon-first. One Go process per instance owns the agent sessions, inboxes, rooms, boards, the file system, language servers and terminals. The desktop application is a window onto that daemon, and the web version, when it comes, is the same pages served remotely, possibly through Tela.

The [remote-control proposal](docs/design/remote-control.md), recorded on 25 October 2026, recommends paired browser access over private-network HTTPS first. It identifies the client identity, authorization, event recovery and concurrent editing work needed beyond the current loopback server. This proposal has not enabled remote access.

The stack:

- **Go** for the daemon, built without CGO.
- **Wails** for the desktop window, kept independent of the front end. The front end talks to Go over HTTP, Server-Sent Events and WebSockets and never through Wails' JavaScript bindings, so the window toolkit is an internal choice that can change without debt. Wails v2 is the stable release; v3, which adds multiple windows, is in beta and can be adopted when it is ready.
- **Plain JavaScript on PUDL** for the front end, with no framework.
- **CodeMirror 6** with `@codemirror/lsp-client` for editors, and ProseMirror for the visual Markdown view.
- **xterm.js** for the terminal, drawing a real pseudo-terminal in the daemon: the documented ConPTY API on Windows and standard pseudo-terminals on Linux and macOS.
- **The git command line** for repositories and worktrees, because it is git's documented interface.
- **Markdown files** as the source of truth for documents and boards, and a pure-Go SQLite (modernc.org/sqlite) for the message bus, the idea inbox, room transcripts and search indexes.
- **ripgrep**, bundled, for search.

### Subscriptions Between Instances

The cheapest transport that works is chosen for each subscription. PUDL is public on GitHub, so its GitHub releases can serve as its release notices, and any instance can watch them through GitHub's documented API without any server of Paul's. A relay of Paul's own is needed only for private libraries and for proposals that should not appear on GitHub.

Anything that leaves the work instance passes through an outbound gate. Release notices arriving at the work instance flow freely. A proposal leaving it waits until Paul has read and approved it, because a proposal written by an agent at work can contain the employer's internal detail.

## Delivery

Paul needs Dinah urgently, so delivery starts with the piece that removes the most copying and pasting soonest, and every stage after that is something he uses on his own work.

### Stage 0: The Message Bus

The first deliverable is Dinah's message bus, which runs before Dinah has a window and is the beginning of the real daemon. The bus keeps the inboxes, rooms, proposals and release notices, and it offers them to agents as an MCP server. Paul registers that server with the Claude Code sessions he runs, and those agents gain tools to send a message or a document to another workspace's agent, to read their inbox, to announce a release and to answer one with a verdict.

#### How a Session Identifies Itself

Paul runs several Claude Code sessions in some workspaces, so the bus must tell sessions apart, and it must do so from what Claude Code documents. The [hooks reference](https://code.claude.com/docs/en/hooks) gives every hook a `session_id`, a `cwd` and the event's name in its input. Nothing in the documentation gives an MCP server the session's ID directly. A hook of `type: "mcp_tool"` closes the gap: it calls a tool on a configured MCP server, and its `input` strings accept `${path}` substitution from the hook's input, so `"${session_id}"` passes the session's ID to the server. Claude Code reads the tool's text result as it reads a command hook's output.

The bus uses four hooks, all configured in Paul's user settings:

- **SessionStart, as a command hook.** At launch the session's MCP servers are not yet available to hooks, and the documentation says `mcp_tool` hooks on SessionStart are skipped then. A command hook, `dinah hook`, therefore reads the hook input from standard input, registers the session with its ID, its project folder from `CLAUDE_PROJECT_DIR` and its title, and adds context telling the agent its name on the bus and who else is there.
- **UserPromptSubmit, PostToolUse and Stop, as `mcp_tool` hooks.** Each calls the bus server's `hook_deliver` tool with `${session_id}` and the event's name. The first call tells that server process which session it serves, and every call returns any waiting messages as `additionalContext`. UserPromptSubmit delivers when Paul speaks to the window. PostToolUse delivers between the agent's tool calls, so Claude effectively accepts messages in the middle of a turn. Stop blocks the end of a turn when messages are waiting, so the agent reads and answers them without Paul typing anything. Stop continues a turn at most three times in a row, which matches the three-hop limit on automatic handoffs. The bus counts the continuations itself and resets the count when Paul submits a prompt or a turn ends with nothing new, so the limit does not depend on how the hook passes `stop_hook_active`. After the third, further messages wait for Paul's next prompt.
- **SessionEnd, as a command hook,** marks the session ended.

The bus never trusts an agent to supply its own session ID. One condition could break the binding: a single server process serving more than one session. The bus detects this, because every session's first prompt fires its UserPromptSubmit hook before its agent can call a tool, so such a process would receive two different IDs. A server process that sees a second ID refuses to attribute tool calls and says why, rather than guessing.

#### Waking an Idle Session

Hooks alone cannot reach a window nobody is speaking to, and Paul ruled out typing "go" into each window as a way of working: he wants rooms that behave like a live chat. Claude Code documents two ways for something outside a session to start a turn in it, and only one of them is usable without relying on undocumented behaviour.

The first is [channels](https://code.claude.com/docs/en/channels-reference). An MCP server that declares the experimental `claude/channel` capability may send `notifications/claude/channel` events, and Claude Code puts each one in front of the agent as a `<channel>` tag. Channels are a research preview. A server that is not on Anthropic's allowlist registers as a channel only when the session is started from a terminal with `--dangerously-load-development-channels server:dinah`, and the documentation does not offer channels in the VS Code extension. Claude Code also drops events silently when a session has not loaded the server as a channel, and it never tells the server which case applies. The reference states that events arriving while Claude is busy are delivered together on the next turn. For an idle session it shows Claude starting to respond in its walkthrough, and that example is the closest the documentation comes to promising the wake.

Dinah's MCP server always declares the capability. Once a hook has told it which session it serves, it checks the bus every second and sends one event when a newer message is waiting for that session. The event only says how many messages are waiting, and the agent collects them with `inbox`. Because the messages stay on the bus until they are collected, a session that dropped the event loses nothing, and its hooks deliver the messages as before. The Go SDK has no method for sending a custom notification, so the server wraps the stdio connection it opens and writes the notification through the documented `Connection` interface, whose `Write` the SDK documents as safe to call concurrently. Claude Code 2.1.306 asks for MCP protocol version 2026-07-28 and then reports that a connection on that version has no channel delivery path, so the server offers versions up to 2025-11-25 only. The channels reference does not say which protocol versions carry channel events, and this restriction should be revisited when it does.

`dinah claude` starts `claude` in the current folder with the development flag and an opening prompt. The opening prompt fires the UserPromptSubmit hook, which is how the bus learns the session's ID, and until that happens the server cannot tell which session's messages to watch for.

A woken agent can wake another, so Dinah enforces the three-hop limit on automatic handoffs at the doorbell for messages outside group chats. A group's messages are not tested against the hop count at all; the group's turn budget decides whether a mention starts a turn (Group turn budgets, below). A message Paul sends is hop 0. A message an agent sends is one hop past the furthest message that agent had read, and Paul speaking in the agent's window, or a message from Paul reaching it, starts the count again at 0. Testing showed that Claude Code fires the UserPromptSubmit hook for a turn a channel event started, which made each woken agent look as if Paul had spoken to it and let a conversation run past the limit. The documentation does not say whether that hook fires for channel turns, so the server handles both cases. After it rings, it treats the next UserPromptSubmit as a doorbell turn that keeps the hop count. If Claude Code stopped firing the hook for channel turns, the cost would be that one later prompt from Paul did not reset the count, which errs toward fewer automatic wakes. The doorbell rings only for messages of hop 3 or less. Later messages still wait on the bus and arrive at the session's next turn, which Paul starts by speaking to it or by posting again. The agents' instructions also tell them not to answer a message that needs no answer, such as thanks.

The second mechanism is [cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging). Each session listens on its own inbox socket, which is a named pipe on Windows, and the documentation says that "when the receiving session is idle, Claude Code starts a new turn with the message." That statement covers sessions in the VS Code extension. Claude Code gives hooks the socket's path and a per-session token in `CLAUDE_CODE_MESSAGING_SOCKET` and `CLAUDE_CODE_MESSAGING_TOKEN`, and a connection that opens with `{"type":"auth","token":"<token>"}` is treated as coming from the session's own child, so its message is delivered without an approval prompt. The documentation does not describe the format of the message line that follows the auth line, so building on the socket would mean relying on undocumented behaviour. Paul decided on 22 October 2026 not to pursue waking VS Code sessions at all. Dinah's own window is where he works with agents, and terminal agents started by Dinah are the bridge.

#### Agents Outside Dinah's Window

Inside Dinah's window every agent runs through ACP, so Dinah sends each prompt itself and can start a turn whenever a message arrives, whatever the provider. Outside the window, Paul starts a provider's own terminal agent with `dinah claude`, `dinah codex` and so on, following the shape of `ollama launch`. The launcher finds the provider's program, adds what joins it to the bus for that launch only, passes the person's own arguments through after its own, and runs the program in the current folder. An outside agent can always send and receive, but whether it wakes when it is idle depends on what its provider documents. Paul accepted on 22 October 2026 that an outside agent with no documented wake reads its messages when it next takes a turn.

`dinah claude` is described in the section above, and it is the only launcher whose sessions wake.

`dinah codex` registers a session on the bus itself, with an ID it makes up, and attaches Dinah's MCP server through Codex's documented `-c` overrides of `mcp_servers.dinah.command` and `mcp_servers.dinah.args`, so the person's Codex configuration is not touched. The server is started as `dinah mcp --session <id>` and serves that session from the start, without hooks. It declares no channel, rings no doorbell, and tells the agent to check its inbox at the start of each turn and between steps of long work. Codex documents hooks, but each new hook must be reviewed and trusted by hash before it runs, and supplying hooks through `-c` is not documented, so the launcher does not use them. Codex documents no way to wake an idle interactive session. `codex queue` comes closest, but the documentation does not say that a queued message starts a turn in an idle session, and OpenAI's own tracker has a report of it failing to.

Because Codex never sends a UserPromptSubmit to the bus, Paul typing in a Codex window does not reset that session's hop count; only a message from Paul through the bus does. This errs toward fewer automatic wakes. Codex asks before each Dinah tool call unless the person sets `mcp_servers.dinah.default_tools_approval_mode`. The configuration reference lists that key's values without saying what each does, so the launcher leaves it unset.

`dinah devin` is deferred. The Devin CLI documents no way to attach an MCP server for one launch, so its launcher would have to write `.devin/mcp_config.local.json` into each workspace. Devin also reads Claude Code's configuration by default, so every Devin session on Paul's machine already loads Dinah's MCP server and Claude Code hooks. Those sessions are not identified on the bus, because the hooks that identify a Claude Code session are of a type Devin does not document, and their bus tools report that the session is not identified. A Devin agent inside Dinah's window runs through `devin acp` and needs none of this.

#### What Agents Can Do on the Bus

The agents' tools are `whoami`, `sessions`, `rename`, `send`, `reply`, `inbox`, `read_attachment`, `room_create`, `room_join`, `room_leave`, `subscribe`, `announce_release` and `verdict`. A message goes to a chat by its title, to a workspace by its folder name, to a group chat as `#` and its name, or to Paul as `paul`. When two chats share a title, the agent adds the workspace in parentheses, as "Fix the Parser (studio)", and a title alone that more than one chat has is refused with the chats it could be. The bus keeps each chat's title in its session's row, and Dinah's window writes it there when the chat joins the bus, when its agent titles it and when the person renames it, so every heading, list and address reads the title as it is now. A chat with no title yet is shown as "Untitled Chat in" its workspace's name in the window, which the window also writes to the bus. `rename` sets the title of a session outside the window; a chat in the window has the title the window shows, so its agent is not offered the tool. The handle the bus once gave each session from its folder, such as `studio-15`, is gone, and a chat is reached by its title alone. A message to a workspace goes to every session open in it except the sender, and when no other session is open it waits for the workspace's next one, so a workspace stays addressable as sessions come and go. Subscriptions are kept by workspace for the same reason.

What the code and the agents' tools call a room is shown as a group chat, and its members are chats and Paul, as Paul ruled on 27 October 2026 ([docs/plans/group-chats.md](docs/plans/group-chats.md)). Paul is always a member. A message that mentions him, which an agent does by putting `paul` in the mentions of its send or reply, makes a card in Notifications and, when the window is not the active one, a notification from the operating system; the window finds such messages in the bus's data, so it makes no difference which process sent them, and the chats are told to mention him when they need him and that his name in the text mentions nobody ([docs/plans/mention-notification.md](docs/plans/mention-notification.md)). A group has a name, which it takes from its chats' titles when it is made without one, and a chat must have a title before it joins a group, since two untitled chats in one workspace cannot be told apart. The rooms of workspaces from before were converted once, each workspace member becoming the chats of that workspace the bus knew at the time, and they kept their messages. A message in a group goes to every member chat except its sender. It wakes only the chats it mentions, and every other member reads it at the start of its next turn, marked as for its information, without keeping a turn going at the Stop hook, which answers open question 2 below for now. The mentions are a list the message keeps, given by its sender: agents pass chat titles in the `mentions` of `send` and `reply`, and the person's @ list in the group's window passes the chats chosen from it, since a title with spaces cannot be found reliably in the text. A mention of everyone wakes the members that are open, a mention of Paul also puts the message in his inbox, and an agent's mention of a chat outside the group is refused with the reason. A closed member keeps the message until it opens, and a message that wakes it opens it in the background (see Chats on the Bus). The group's own messages count as unread for Paul until its window shows them, and a group keeps a line for each chat added or removed. `room_create` takes its members by title, and `room_join` and `room_leave` act on the calling chat.

The Group Chats pane, which was the Bus pane, shows Paul's inbox, the group chats, every chat the window knows by workspace with its state, and the trusted links. A chat's state is Working, Open, Open in Background or Closed. New Group Chat… in the pane, and Start a Group Chat… and Add to a Group Chat… in a chat window's Actions menu, open the picker, a window with an address that keeps the chats ticked. A group's window shows its members as chips with their states and menus, its conversation, and a box whose @ list offers its members. A group has no Leave, since Paul is always in it, and Delete Group… keeps its messages.

An agent's attachment is a file in the sender's own workspace, recorded with its path and SHA-256 hash. A recipient reads it through `read_attachment`, which returns the current content and says whether the file has changed since it was sent. Only the sender and the chats the message reached can read the attachment, and a sender cannot attach files from outside its own workspace, so the bus already follows the zero-trust rule for documents.

Paul attaches files to his messages in a group chat as in a single chat: pasted, dropped on the group's window or chosen with Attach…, up to 25 MB each ([docs/plans/group-attachments.md](docs/plans/group-attachments.md)). He has no workspace, so the bus copies each file into Dinah's home folder, under `attachments` and the date, and records the copy as an attachment of his message with its name, type and hash. The chats his message reached read it with `read_attachment` by the same rule, and a picture comes back as an image. When the message is delivered to a member chat whose agent says in `initialize` that its prompts take images, each picture also goes in the prompt as an image block, as a pasted picture does in a single chat; every file is listed with its name, type and size. A copy lasts as long as its message, until Paul removes the attachments older than an age he chooses in Settings › Chat; the message stays and shows each such file as removed, and an agent reading one is told it was removed.

Agents are told when they join that a message from another agent is a request to weigh, and that before changing files or running commands because another agent asked, they check with Paul unless he has said that link is trusted.

#### Storage and the Bus's Page

The bus keeps its state in one SQLite file in Dinah's home folder, which every `dinah` process opens in WAL mode. The MCP server processes, the hooks and the page therefore need no daemon to talk to. When a daemon takes over the file, the MCP processes become thin clients of it. That change is internal, and the agents' tools stay as they are.

`dinah serve` runs a page for the bus on the loopback address: Paul's inbox, the group chats, the releases and who is on the bus, server-rendered in PUDL with a URL for every group chat, thread and release, refreshed when the bus changes. It accepts only requests addressed to its own host name and port, which defeats DNS rebinding. Every request needs a cookie that `dinah open` sets through a single-use code, and every form post must come from the page's own origin, so no web site Paul visits can post a message into his agents' context. The bus's views move into Dinah's window as applets in milestone 4 below.

### Stage 1: The Window

On 22 October 2026 Paul asked for a functional GUI before anything else: Dinah's own window in PUDL's windowed mode, with a virtual file system usable for real work, workspaces, and working Chat, Files, Terminal and Editor apps. Dinah is windowed only; it has no Classic view. Communication between workspaces is the need he feels most, and it must be frictionless.

#### The Shell

Dinah's shell is a workbench of window kinds with a Workspace sidebar and docked browsers for chats and notifications. A command registry, declared once, feeds the menu bar, Keyboard Shortcuts, command search and agents; the host's menus come from `pudl-menubar.js`, and the front window adds its own beside them. Settings has Appearance, Agents, Chat and Diagnostics, and Settings › Agents sets up Claude, Codex, Devin and Ollama. Workspaces are named sets of local folders, presented through the file system with file watching; Files browses them and the Editor edits documents through drafts, so closing a window loses nothing. Skills are kept per workspace and run as chats.

Starting a chat is the shell's clearest rule. New Chat, from the Workspace sidebar or the menu, opens a draft chat window in the active workspace at once, with the provider, mode and model as menus in its composer, and the agent's session is made when the first message is sent; the workspace can be changed before then. The chat's composer offers `/` for skills and `@` for windows, applets, files and other open chats, queues and steers while the agent works, and shows approvals, plans and a context meter. What is typed in a chat's box, a group's or a thread's and not yet sent is kept across a restart in the saved UI state in Dinah's home folder ([docs/plans/group-chats.md](docs/plans/group-chats.md), Drafts Across a Restart).

Every applet offers typed actions that agents discover and invoke through the applet MCP tools, including one chat asking another.

**An exception to the Architectural Principles.** The principles call for server-rendered pages with progressive enhancement and no single-page application framework. Dinah's shell is drawn in the browser by its applets from calls to Go. Paul chose that model for the shell on 22 October 2026, so the shell is an explicit exception. PUDL's windows still keep their arrangement in the address, and no framework is added: the applets are plain JavaScript.

#### The Window and Its Transport

The window, `dinah-desktop`, runs a server on `127.0.0.1:47616` for the page, its files and the bridge to Go, and loads it as a browser would. The window does not use Wails' asset server for the page, because the page depends on streamed responses and Wails' documentation does not promise that its asset server streams; Wails' own page only signs the window in and sends it there. The sign-in page moves on to the desktop with a page of its own rather than a redirect, because a navigation that began on Wails' page makes a redirect chain cross-site, and a browser withholds a SameSite=Strict cookie from such a chain.

`internal/bridge` carries the front end's calls to Go and Go's events back. It serves the App's exported methods at `/bridge/call`, a generated `/bridge/app.js` that defines `window.go.main.App` with one function per method and `window.runtime`, and the App's events at `/bridge/events` as Server-Sent Events. The script lists exactly the App's methods, so the front end's checks for whether a method exists keep their meaning. The front end therefore never depends on Wails, which honours the decision of 21 October. Native dialogs, such as choosing a folder, stay in Go, in the window's process. An event that carries the whole of some state, such as a session's information, its queue, a provider's state or the settings, also carries a generation and a version (`stateGen` and `stateVer`) taken from its owner's counter in the same critical section that copies the value out. The events are still emitted after the owner's lock is released and so can arrive in the wrong order, and the page ignores one whose version is lower than the one it already holds for that owner. A resync's reread of the same state returns the same two fields and is ordered by the same rule. The shape is in [docs/plans/state-versions.md](docs/plans/state-versions.md). A window opened on a chat that is live in the engine draws the chat's saved copy and then the chat's event log from the number the copy is consistent with, which the history records when it writes the file, so that a turn in progress is shown with what it has said so far ([docs/plans/running-chat-catch-up.md](docs/plans/running-chat-catch-up.md)).

Only the window reaches the server. The Host must be the server's own, the cookie comes from a one-time code that Wails' page hands the window, a call must come from the page's origin, and the page's Content Security Policy runs only the page's own scripts, so HTML that reaches the page cannot run as script. Opening an address in the browser accepts only web and mail addresses, for the page and Go alike. A single-instance lock keeps one window, so a second copy cannot save over the first's settings. Files dropped from the system's file manager arrive as an ordinary browser drop, because Wails' file drop reaches only a page Wails serves itself: the page posts their contents to `/upload`, where they follow the same rules as an upload by path, streamed to disk as they arrive. Setting `DINAH_SHELL_ENTRY_FILE` makes the window start hidden and write a one-time sign-in address to that file, so a browser can drive the live page under test without a window appearing.

The window is a separate program from `dinah` because a Windows GUI program cannot print to the terminal it was started from, which the command line needs. `dinah install`, run from Dinah's source folder, builds and installs both.

#### Consent for a Chat's Applet Actions

A chat reaches every applet action through one MCP tool, so a provider's approval of that tool cannot tell a read from a write, and one "allow" for a read would allow every write. Dinah therefore asks the person itself before an action from a chat has an effect: writing workspace files, changing settings, running a window's command, or asking another chat (`applet.Effectful`). The question appears in the chat and in Needs You, through the same mechanism as an agent's own permission requests, with Allow, Always Allow in This Workspace and Don't Allow; reads run without asking. Settings › Agents lists the actions allowed always and forgets them. The broker takes the host's consent as a hook and holds no policy of its own. Trusted links between workspaces will build on this, since a trusted link is a standing consent between two workspaces' agents.

#### Chats on the Bus

Chat requests and replies follow the [chat messaging design](docs/design/chat-messaging.md), approved by Paul on 24 October 2026. New applet questions deliver their results automatically to an idle caller, or after a busy caller's active turn, and every provider receives the communication protocol with each prompt. Paul also approved mentions across workspaces and direct name lookup on that date. Open chats carry workspace labels, and ambiguous names require an explicit choice rather than an automatic guess.

Every chat open in the window is a session on the bus, whatever its provider. The window registers the chat itself, in the chat's workspace, and keeps the chat's bus session in its settings so a reopened chat comes back under the same name. It gives the chat's agent the bus's tools through a server of its own, `dinah-desktop --bus-mcp`, which it lists among the MCP servers of the chat's ACP session; ACP requires every agent to support such stdio servers. The server is named `dinah-bus`, because the person's own Claude Code settings may start a server called `dinah` in the same agent.

Delivery belongs to the window, since it sends every prompt. Once a second it looks for chats that are idle and have messages waiting within the hop limit, or, for a group's messages, within the group's turn budget, marks such a chat working, takes its messages from the bus and starts a turn with them. A chat that is working is never interrupted, and its messages wait for the turn to end. When the person writes to a chat, any messages waiting for it go to the agent with the person's words, and the hop count starts again, as a person's prompt does in a Claude Code session. No hooks and no channel are involved, so Claude, Codex, Devin and Ollama chats are woken the same way.

A message that asks a chat to answer reaches it even when the chat is not connected, as Paul ruled on 27 October 2026 (docs/plans/group-chats.md). Such a message is one sent to the chat itself, a group message that mentions it, or a reply it waits for; a message to a workspace, and a mention of everyone, wake only chats that are open. The watcher connects the chat through the path the prompt's Reconnect Now button takes, so a chat whose window was restored and waits at that prompt reconnects in its window, and a failure is reported there as the prompt reports it. A chat with no window is opened the same way without one and is then Open in Background, with its own state in every list. At most three chats are open in the background at once and the rest queue in order. One closes itself thirty minutes after its last turn ends unless the person has opened its window: it leaves the bus, its messages wait for it, and it stays in its groups. Dinah keeps its session with the agent, so it comes back without being loaded a second time. A chat that fails to connect is asked for again only when a newer message wakes it, and its messages keep waiting. Since the messages wait on the bus, a restart pokes their chats at the watcher's first look. When the window starts, the chats that belong to groups with a message in the last seven days are also opened in the background ahead of any message (Paul, 29 October 2026), so that a mention finds them ready. At most four are opened, in the order of their groups' latest activity, two at a time, and they do not use the three background slots; they close like any other background chat, and a failure is not retried. A message that waits for a chat which is still restoring or replaying its saved conversation is shown in that chat at once as arriving, and the delivered message replaces it when the chat is ready. The shape is in [docs/plans/group-reopen.md](docs/plans/group-reopen.md).

The chat shows each delivered message as a card of its own, never as something the person typed, whether it came in a turn of its own, with the person's words, or as steering. The card's head says what the message is and who sent it, such as "Reply from PUDL Development" or "Message from Parser Release (workspace Parser)", with a result's status as a glyph and a word, and the row's time is when it was sent. A card shows the sending chat by its title as it is now, so the card follows a chat that is renamed, and a chat no longer open keeps the title it had when the message came. Its body is the message as Markdown, folded behind PUDL's disclosure when it is long. The chat's saved copy keeps each message as an entry with the role `delivered`, holding the message's bus ID, kind, sender, workspace, time and readable text (`bus.Describe`, which leaves out the instructions the agent is given about answering), and the first entry of each delivery also keeps the text of the prompt the agent was given. The agent's prompt is unchanged. When a chat reopens, the agent replays that prompt as a user message. Dinah holds each replayed user message until it ends, joins its pieces and compares the text with the runs of the person's words and deliveries in the saved copy; a match is drawn and kept as those entries, and anything else goes on as the agent sent it. The comparison uses only Dinah's own record of what it sent, never the agent's chunking or the bus's prompt format. A handoff to another provider, its summary and an exported chat give each delivered message under its sender. Chats saved before this keep their old rows.

The agents the window runs load the person's Claude Code settings, Claude through the Agent SDK and Devin by default, so they also start `dinah mcp` and run `dinah hook`. Left alone, those would put each chat on the bus a second time under the agent's own session ID. The window therefore sets `DINAH_HOSTED` in the environment of the agent processes it starts. Claude Code documents that a hook process inherits the parent environment, so `dinah hook` sees the variable and does nothing, and `dinah mcp` serves no tools and tells the agent to use `dinah-bus`. The hooks standing down rests on that documented inheritance. The `dinah mcp` copy is tidied by the same variable where the agent passes its environment to MCP servers, and where it does not, that copy only offers tools that report the session as unidentified.

#### Correctness and Shared Pieces

Live views follow the [shared rendering contract](docs/design/chat-rendering.md). One event-driven frame queue coalesces their updates, rotates unfinished work within a cooperative 6 ms budget and defers hidden views until they are visible. Chat output, lists and Bus views share that budget. Agents and message delivery continue independently of rendering. Paul approved this on 24 October 2026 after concurrent command streams caused input stalls.

A review of the shell's code on 23 October 2026 found these problems, which Dinah fixes as it goes: no Content Security Policy on the main page (fixed), script reachable through a paste into the visual Markdown view, applet actions from a chat with no consent per action (fixed), a second copy of the app overwriting the first's settings (fixed), links that open network paths (fixed for addresses opened in the browser), an ACP read loop that can hang, agent processes that outlive Stop, a Codex cancel that closes every Codex chat, a write guard that leaves Claude's permission rules open, and a chat that redraws a streaming message in full on every frame. The review also found the same small tasks solved several times over, and Dinah builds one shared piece for each as it touches the code: one atomic file write, one way to change settings (`updateSettings`, in use), one JSON-RPC transport, one provider lifecycle, one process runner with a job object, one containment rule for paths, and one front-end module for escaping and sanitising HTML.

#### The Terminal

The Terminal runs real shells: whatever Paul chooses, PowerShell, cmd, Git Bash, WSL's bash or ssh among them, through Windows' documented pseudoconsole API. A workspace's terminal starts in the folder that backs it, because a real shell sees the disk rather than Dinah's file system. Its front end is parkscomputing.com's xterm.js 6 Terminal applet, the most current of Paul's terminal front ends, carrying a real terminal's bytes in place of its own interpreter.

`internal/pty` follows Microsoft's "Creating a Pseudoconsole session" step by step: two pipes, `CreatePseudoConsole` over their far ends, the shell started with the pseudoconsole as a process attribute, `ResizePseudoConsole` as the window changes size, and `ClosePseudoConsole`, with the output drained on its own goroutine as the documentation warns. Each shell is started outside the app's lifetime job (`internal/procjob`, which the agents and extensions stay in) and runs in a job of its own, whose only handle Dinah holds, so the shell ends when Dinah does in any way. That job lets the shell's children break away silently, so a windowed program such as Notepad or `code .`, or a console program that has left the console, is in no job of Dinah's and outlives both its Terminal and Dinah. Closing a Terminal closes the pseudoconsole, which ends the shell and the console programs attached to it, and ends the shell itself if it is still running 5 seconds later. The window closes every Terminal before it exits, so attached console programs end with it; after a crash they may not. docs/design/terminal-shells.md explains why the close event alone is not enough, how the shell leaves the lifetime job, and the limit after a crash. The shell is started without `STARTF_USESTDHANDLES`, so by the STARTUPINFO documentation its standard input and output are the console's buffers. Whether a child instead takes its parent's own standard handles, when the parent has some, is not documented, and testing showed that it does; so the window gives up its standard handles with `SetStdHandle` as it starts, which it never uses, being a Windows GUI program, and the question does not arise.

The window finds the shells where their installers put them: PowerShell on the PATH, Windows PowerShell and the Command Prompt in the Windows folder, Git Bash beside the git on the PATH or in Git's default folder, and WSL. Dinah's own shell over its file system stays as one of the choices. Settings › Terminal chooses the shell a new Terminal runs, and Tools › New Terminal With runs another. What the shell draws reaches the page as events of base64 bytes, so a character split between two reads arrives whole, and typed text goes back one call at a time in order. Ctrl+C copies when text is selected and interrupts otherwise, as in Windows Terminal, and Ctrl+Shift+C and Ctrl+Shift+V always copy and paste.

Three pieces of work Paul approved on 23 October 2026, after he tested Steer with a Claude chat, are done:

1. Steering a Claude chat without ending its turn. Steer used to cancel the turn and send the steer as a new prompt, so whatever the agent was doing was lost. For a Claude chat, Steer now queues the message on the bus, and Claude Code's documented PostToolUse hook hands it to the agent as additional context before its next step, or the Stop hook hands it over and continues the turn if no further tool call comes. Inside Dinah's window the person's hooks reach the stand-in `dinah mcp`, which knows only Claude's own session ID, so each prompt a Claude chat sends carries a marker line with the chat's bus session, and the UserPromptSubmit hook, whose documented input includes the prompt, passes it on and ties the two together. Claude uses hook delivery once its hooks have established that binding. The shared steering contract now also supports Codex, Ollama and Devin; a delivery path that is unavailable queues the input without cancellation, as described in [docs/design/steering.md](docs/design/steering.md). A steer no hook took by the end of the turn is withdrawn and sent as the next message, so it is never lost. Stop and Steer, in a chat's commands, still drops what the agent is doing.
2. Showing a pending steer in the chat. While a steer waits for the agent's next step, its row says so, and then says delivered once a hook hands it over, or sent when the turn ended first.
3. Leaving out an unchanged Editor selection. When the Editor's selection has not changed since the chat's previous message, Dinah leaves it out, so a selection left behind in another document is not attached to every message as its subject.

The hooks that pass the prompt are printed by `dinah setup`. A `dinah mcp` started before that build refuses the extra input, so the person's settings take the new UserPromptSubmit hook only once the Claude Code sessions running the old program have restarted.

A Claude subscription's chats are shown for what they cost. Claude's adapter reports the account it runs on (`_auth/status_update`, an extension it advertises in `agentCapabilities._meta.authStatus`), and when a subscription pays, Usage shows the adapter's figure as the price at API rates, covered by the plan, and the turn line shows no price.

Trusted links came in milestone 4. Paul can mark a link between two workspaces as trusted, and the agents on either side then act on each other's requests without asking him; without one, an agent still checks with Paul before changing files or running commands because another agent asked. Each trusted link has its own limit on automatic handoffs, offered at ten against the default of three, and Paul can turn the limit off for a link entirely after a warning, because two agents with no limit can keep each other working, and spending, for as long as Paul leaves them.

The bus keeps the links in its own file, so every process applies the same ones. A link runs both ways, and only Paul makes or removes one, from the Group Chats pane; agents have no tool for it. A workspace may trust itself (29 October 2026): the three-hop limit also stops chats of one workspace that work together, as the Dinah Cleanup group's architect and two implementers found when their third exchange waited for Paul to speak, and a link from the workspace to itself raises or removes the limit between its own chats. Once groups have turn budgets, the group no longer needs that link, which then affects only direct messages between the workspace's chats. The doorbell uses the link's limit between the sender's workspace and the recipient's in place of three, and a message delivered across a link says so, telling the agent it may act on the message as on a request from Paul. The list of who is on the bus, which agents see when they join and through `whoami`, lists the links with their limits.

Group turn budgets (29 October 2026). A group chat has a turn budget in place of the hop limit, and the default is none. The bus keeps two numbers on the group: the budget, which is unlimited or a count of turns, and the turns used since Paul last posted in it. One turn is used each time the bus hands a chat one or more messages from agents in the group that ask the chat to answer, whether that starts a turn or reaches a turn already running. Messages handed over together count once, so five messages to one chat from one turn use one, and a message that mentions three chats uses three. The bus counts them itself, in the transaction that hands the messages over, so the count does not depend on the window reporting when a turn starts. A post from Paul in the group sets the used count back to 0, as does choosing a new budget, and Paul's own messages are never counted or held. The doorbell and the reopening of closed chats test a group's message against the budget and every other message against the hop limit. When a group's budget is spent, its mentions are still delivered and wait for the chat's next turn, and a chat that reads one is told it is background and not a request, until Paul posts. Only Paul sets a budget, from the group's header, and agents have no tool for it. Messages in a group do not advance a chat's own hop count, so a long session in a group leaves its members' direct messages inside the limit. The cost is that nothing guards a loop which alternates between direct messages and a group's mentions: each direct leg is counted from the start again after a group leg, and a group with no budget does not count its own. A group the person wants guarded against that needs a budget. The group list shows a budget only when one is set.

Flows come back later; Paul counts them as a feature Dinah must have.
