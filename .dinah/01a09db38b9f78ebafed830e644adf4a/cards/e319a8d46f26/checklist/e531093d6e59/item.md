note: "Rewritten at round 4. Round 3 decided to extract the two commands wired through inline handlers, `dinah.tree.checkWorkbench` and `dinah.tree.openAttachment`, so that AC-19 would need no exemption list. The reviewer showed that this bought the wrong half. Extracting a function makes it importable; it says nothing about which command id the editor wires it to, and AC-19's whole purpose was that the thing driven is the thing registered. A test holding its own id-to-function table would have been a fourth independent list beside the manifest, `TREE_COMMANDS` and `SELECTION_POLICIES`, with nothing holding it to `extension.ts`.\n\nThe reviewer offered two ways out and this is the second. The first was to keep the extraction and add a compiler walk asserting that the identifier registered for each id is the identifier the test's table names. That works for the ids that sit in an array literal as `[ID, fn]` and does not work for the six registered through an inline arrow that calls a named function inside its body, where recovering \"the function\" means guessing which call in the body is the one that matters. That is the guard-widened-by-example shape this board has paid for twice, on dinah-424 and dinah-439, and the answer both times was to stop inferring and read a declaration instead.\n\nSo the declaration is minted. `ROW_COMMAND_TABLE` holds one `{ id, invoke }` per row command, `activate()` iterates it in a single `register` call, and the four `noRow` commands keep their own calls because they read no row. AC-19 imports the table and drives the entry; AC-3 asserts the registration shape and that the table's id set is exactly the non-`noRow` half of `SELECTION_POLICIES`. Nothing about any command's behaviour changes, and the existing tests for `checkWorkbench`, `openAttachment` and every other command go on driving the same inner functions unedited.\n\nWhat makes the module possible is that nothing it needs imports vscode: searching the whole of `src/` at 4c33c2c found `extension.ts` as the only module importing it as a value, so `cardCommands.ts`, `workbenchCommands.ts`, `columnCommands.ts`, `pullCommands.ts`, `creationCommands.ts`, `diagnostics.ts` and `tree.ts` are all reachable from the unit layer already. The two values that used to force a closure, the `diagnostics` object and the channel, become `applyCheckResult` and `appendLine` on a `Wiring` record `activate()` supplies at call time, declared structurally so the table module names no type belonging to a `DiagnosticCollection`.\n\nThe cost is honest and worth stating. This is a larger change to `extension.ts` than round 3's, it lands at round 4, and it moves code no criterion on this card would otherwise have touched. What it buys is that the card's central wiring guard becomes implementable at all, and the alternative was a criterion nobody could satisfy."
