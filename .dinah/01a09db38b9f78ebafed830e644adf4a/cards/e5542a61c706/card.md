Every agent dispatched with the harness's built-in worktree isolation gets a worktree under `.claude/workspaces/`-style paths inside `C:\Users\paul\source\repos\dinah\.claude\worktrees\`, which is the one placement the workbench instructions forbid. The instructions give the reason: dinah discovers a workbench by climbing from the working directory to the drive root, `DINAH_HOME` does not bound that walk, and the repository carries its own `.dinah` at its root, so an agent running the binary from in there reaches a real workbench while believing it is sandboxed. The workbench document "Working safely against the operator's own data" exists because that has already gone wrong once.

Three consecutive stages on dinah-120 hit it. The first refused outright and blocked the card, correctly, because its pass was the one that had to run the test suite. The second and third worked around it by naming a prepared scratch worktree explicitly on every single command. The workaround holds only as long as each agent remembers it on every command, and the next one that forgets does real damage silently.

Passing a pre-created worktree does not help, because the harness pins the session before the agent starts and the agent has no tool that can move its own session afterwards. So the instruction "work in this worktree" cannot be honoured by the agent it is given to; it can only be approximated per command.

The cause is that the dispatching session passes the harness's `isolation: "worktree"` parameter, which is documented in the operator's own memory as the wrong tool on this repository precisely because it creates its worktree under `.claude/worktrees/`. The column directives say `isolation: worktree`, and a dispatcher reading that literally reaches for the built-in.

Two things want deciding, and the second is the one that lasts. Immediately, the dispatch path should stop passing the built-in isolation for this repository and instead create the worktree itself under `C:\dinah-scratch\<card>-<stage>\wt`, detached on `origin/<branch>` when the branch exists and on `origin/main` when it does not. Longer term, the column directive is ambiguous: `isolation: worktree` names a mechanism whose only available implementation on this board is the forbidden one. It should say where the worktree goes, or the board should carry the scratch root as a directive of its own, so a dispatcher cannot satisfy the letter of the directive and violate the instructions at the same time.

Also worth a sweep: several agent worktrees are currently sitting in the forbidden directory from today's dispatches. None appears to have written to live data, because each carries the repository's own committed `.dinah` which stops the climb, but that is luck rather than design and it is one missing file away from not being true. Remove them, and check whether anything under `~/.dinah` was touched today.

## Specification

## What is confirmed, and how

`scripts/hooks/deny-destructive-git.py` reads `PreToolUse` payloads for `Bash|PowerShell` and refuses a mutating git verb that carries no `-C <linked worktree>`. It never reads `payload["cwd"]`, by design (`dinah-233` OQ-9), so it has no opinion about a non-git command and no opinion about a git command outside its deny set. `.claude/settings.json` registers exactly two hooks: this guard on `PreToolUse`, and `andoneer-session-tokens.py` on `Stop`. Neither writes a log of where a session actually stood. `scripts/hooks/andoneer-session-tokens.py:17` mentions `record-isolation-cwd.py` in a comment, but no file of that name exists anywhere in this repository's history (`git log --all -S"record-isolation-cwd"` finds the string only in the comment itself), and nothing registers it. The sibling `Andoneer` repository does carry a working file at that path (`scripts/hooks/record-isolation-cwd.py`), a passive `PreToolUse` recorder that appends one JSON line per Bash/PowerShell call to `.claude/isolation-audit.jsonl`, and it is not registered in that repository's own `.claude/settings.json` either. So the finding in the card description holds: nothing in this repository observes or gates where a shell call actually runs, apart from the narrow git-verb guard above.

The isolation self-check protocol quoted in this card's own dispatch brief, and the worktree-creation discipline it prescribes, live in six files under `~/.claude/agents/` (`card-code-review.md`, `card-implement.md`, `card-merge.md`, `card-review.md`, `card-spec.md`, `card-test.md`). None of those files, and no `.claude/agents/` directory at all, exists inside this repository (`ls .claude/agents/` finds nothing). They are Claude Code's global, per-machine agent definitions, shared by every project on the machine that does not carry its own project-scoped override; the `Andoneer` repository does carry its own `.claude/agents/card-spec.md`, and it differs from the global copy, which is how a project overrides the global one. Dinah has landed no such override. Two consequences follow. First, `dinah-228`'s contract (the self-check itself) is prose this repository cannot enforce by a build or a test, because the prose does not live in this repository's tree. Second, the Andoneer column directive `isolation: "worktree"` (present today on the Spec, Implement, Agent Code Review, Test and Merge columns) is inert data: no code anywhere in this repository's Go sources reads the string `"isolation"` (`grep -rn isolation internal/ cmd/` turns up nothing outside a comment in `internal/testenv`), so the directive means whatever the session dispatching against it decides it means, and the harness's own built-in worktree-isolation parameter happens to share the same literal value, `"worktree"`.

Put together, three different things are being asked of one string. The harness reads `isolation: "worktree"` as a request to allocate its own worktree under `.claude/worktrees/` inside this checkout, which the workbench instructions forbid, because Dinah's workbench discovery climbs from the working directory to the drive root and a worktree inside the checkout sits below the checkout's own `.dinah/`. The workbench instructions read the same string as a request for the agent to build its own worktree under `C:\dinah-scratch\` by hand. And the self-check protocol, which is what actually runs, treats every session that received neither as standing in the main checkout by default and tells it to work there by explicit path from now on. Nothing stops the first reading from being the one a dispatcher acts on, and nothing stops a session's very first tool call, before the self-check has run at all, from mutating something in the main checkout.

## What this card builds

Two independent pieces. Neither depends on the other landing first, and both are additions beside the existing guard rather than edits to its deny-set or its cwd-blind contract for mutating git verbs, which `dinah-233` OQ-9 already settled and this card does not reopen.

### 1. A second, cwd-keyed guard: `scripts/hooks/deny-main-checkout-cwd.py`

Registered in `.claude/settings.json` as a second entry under the existing `PreToolUse` block with `matcher: "Bash|PowerShell"`, alongside `deny-destructive-git.py` rather than merged into it.

**What it reads.** The payload's `cwd` field, and the command text, for every Bash or PowerShell call.

**Classification.** It imports `worktree_kind` from `deny-destructive-git.py` in the same directory (the function at line 735 of that file, which returns `"linked"`, `"main"`, or `"unknown"` by comparing `git rev-parse --git-dir --git-common-dir` for the candidate directory), using the same guarded dynamic import Andoneer's recorder already uses for its own sibling call (`load_in_worktree` in that repository's `record-isolation-cwd.py`), with `sys.dont_write_bytecode` held true for the duration so importing the sibling on every call does not leave a `__pycache__` directory behind. It classifies `payload["cwd"]` once per call.

**When `worktree_kind(cwd)` is `"linked"` or `"unknown"`, the guard allows the call without reading the command text at all.** `"unknown"` covers a `cwd` that is not a git working tree, or a `git` binary that will not run; refusing every command on that answer would turn this guard into a global command-killer whenever `cwd` names something outside any worktree of this repository, which is a wider claim than this card is making. This guard has an opinion about one repository's main checkout, not about every directory on the machine.

**When `worktree_kind(cwd)` is `"main"`, the call is refused unless the command matches one of three forms, checked in this order:**

1. **Byte-exact match** (after stripping only leading and trailing whitespace) against one of the two commands the workbench's own isolation self-check prescribes: `git rev-parse --path-format=absolute --show-toplevel` or `git worktree list --porcelain`. Exact-string match, not prefix match: `git rev-parse --path-format=absolute --show-toplevel && rm -rf x` does not clear this form, because a prefix match would let anything appended after a recognized string ride through on that string's permission.

2. **A leading `git -C `** at offset 0 of the command (case-insensitive on the word `git`, mirroring the `GIT_C` pattern at line 604 of `deny-destructive-git.py`), whose value, read the same way `named_directory` (lines 806–814) and `C_VALUE` (line 608) already read a `-C` argument in that file, resolves through `windows_drive_spelling` (line 773) and then through `worktree_kind` to `"linked"`. `-C` naming `"main"` or `"unknown"`, a missing `-C`, or a `-C` value that is a shell variable rather than a literal path, are all refused, for the same reasons `deny-destructive-git.py` already refuses each of those shapes for the verbs in its own deny set.

3. **A leading `cd ` or `cd "`** at offset 0, followed by the literal separator ` && ` before anything else in the command. The single path segment between `cd ` (or `cd "`) and that separator, with one matching pair of surrounding double quotes stripped if present, is resolved the same way as form 2 and must classify `"linked"`. Only the first such segment is read; a second `cd` anywhere later in the command is not chased, and a command whose `cd` is not the first four or five characters of the trimmed text (`echo hi; cd <worktree> && ...`) does not clear this form.

Anything else, run with `cwd` classified `"main"`, is refused. The refusal names which of the three forms was checked and how the command failed each one, and quotes the two exact self-check commands and the `-C <worktree>` / `cd <worktree> && ` shapes that would clear it, in the same style `deny-destructive-git.py`'s own `DEFAULT_REMEDY` already does.

**Why it stops at these three forms and does not try to determine where an arbitrary command "really" runs.** `deny-destructive-git.py`'s own header records three rounds of a parser that tried to work out where a command runs by following `cd`, subshells, heredocs and quoting, and records seven leaks found by a reader and none by a 167-case suite before the file abandoned that approach for git verbs. The same trap reopens for a guard scoped to every command rather than to git alone: `payload["cwd"]` is fixed for the whole call before the shell starts, so it cannot see a `cd` embedded in the command text, and a guard that tried to verify a `cd` actually took effect by the time some later, unrelated command ran would be reconstructing exactly the shell grammar this repository has already found unbounded. Forms 2 and 3 above ask a narrower question than "where does this command run": they ask whether the command's own first characters name a linked worktree in one of the two literal shapes the workbench instructions already require every agent to write. A command that does not open with one of those two shapes is refused for not saying where it runs, which is the same standard the existing guard already holds mutating git verbs to.

### 2. The recorder, ported and registered: `scripts/hooks/record-isolation-cwd.py`

Ported from `C:\Users\paul\source\repos\Andoneer\scripts\hooks\record-isolation-cwd.py`, with one required adaptation: that file's `load_in_worktree()` imports a function named `in_worktree(path)` from Andoneer's own copy of `deny-destructive-git.py`, a two-valued predicate. This repository's copy of that file exports `worktree_kind(target)` instead, three-valued (`"linked"` / `"main"` / `"unknown"`), because the two files diverged after this repository's own `dinah-233` landed. The ported recorder's `build_record` must set `cwd_in_worktree` to `True` when `worktree_kind(cwd) == "linked"`, `False` when `"main"`, and `None` when `"unknown"`, rather than calling a function this repository's guard does not have. Every other line of the ported file, including its fail-soft posture (every exception swallowed, every exit code 0, nothing ever printed to stdout), its log rotation at 8 MiB, its `IDENTITY_BEARING` environment-variable allowlist, and its refusal to log a payload value longer than 512 characters, carries over unchanged. It is registered in `.claude/settings.json` as a third, independent `PreToolUse` entry under the same matcher, never merged into either guard's file: Andoneer's own header for this file states the reason (`andon-730 D-1`) already, that one shared exception handler between a guard and a recorder would silently turn the guard advisory the day somebody edits the shared code for the recorder's sake, and that reasoning applies here without change.

### Column and workbench directives

The board configuration that names these two mechanisms is Andoneer-hosted data with no representation in this repository's tree, so this card's diff does not touch it; the change is applied directly against the live board.

- The `isolation` directive on the Spec, Implement, Agent Code Review, Test and Merge columns changes value from `"worktree"` to `"scratch-worktree"`. The new value shares no text with the harness's own built-in isolation parameter (`"worktree"`, per the workbench instructions' own description of it), so a dispatcher can no longer satisfy the directive's literal value by requesting the harness's built-in mechanism; the two are textually distinct rather than one being a special case of the other.
- A new workbench-scope directive, `scratch_root`, is set to `C:\\dinah-scratch`, inherited by every column through `effective_directives` (confirmed empty of any workbench-scope directive today by `get_column(fields="effective_directives")` on the Spec column, which currently reports its `effective_directives` identical to its own `directives`). This is the same value six agent definitions and the workbench instructions already spell out in prose in six separate places; giving it one home as structured directive data is the same move `dinah-228`'s own D-1 already made for the two comparison values that self-check needs, carried one step further from prose into data.

## Decisions

- **D-1.** The new guard reuses `worktree_kind` from `deny-destructive-git.py` rather than re-implementing worktree classification, so the two files cannot come to classify one directory two different ways. Same reasoning `deny-destructive-git.py`'s own header already gives for keeping its two internal readings of a span as one function called twice rather than two copies.
- **D-2.** `worktree_kind(cwd) == "unknown"` fails open. This guard has an opinion about the one repository it ships inside; a `cwd` that names no worktree of that repository at all is outside what this card is claiming to protect, and refusing every command whenever `git` cannot classify a directory would turn a repository-scoped guard into a machine-wide one.
- **D-3.** Forms 2 and 3 read only the command's first characters and chase no second `cd` or `-C` later in the text. A command needing more than one hop to reach its worktree is a command this guard refuses, which is the same direction `deny-destructive-git.py` is already permitted to be wrong in.
- **D-4.** The recorder and the new guard stay two files and two independent registrations, per the reasoning already on record in Andoneer's own copy of the recorder.
- **D-5.** Worktree cleanup and the shell-bricking defect in the existing guard stay on their own cards (`dinah-291`, `dinah-219`), both already in flight, rather than folding into this one.
- **D-6.** The column-directive rename replaces `"worktree"` with `"scratch-worktree"` rather than any other spelling, chosen only because it shares no text with the harness's own parameter value; the operator's ruling on OQ-1 below governs the guard's scope, not this rename, and nothing here blocks on that ruling.

## Open question

**OQ-1.** The new guard denies any command run with `cwd` at the main checkout that matches none of the three allowed forms, with no exception for the operator's own interactive session working there directly, because no signal available in this repository or in the `PreToolUse` payload is established as reliably telling that session apart from a dispatched agent's. Three ways to close this, and a fourth is welcome: (A) the guard applies to every session alike, and the operator disables it locally through `/hooks` for the stretches where he is working the checkout directly; (B) the guard exempts the operator's own interactive sessions on a signal he sets himself in his own shell profile, understanding that whether such a signal reaches, or fails to reach, a dispatched subagent's own shell calls is not something this card has verified and cannot verify without relying on Claude Code's own environment-inheritance behavior between an orchestrating session and the subagents it dispatches, which is not established as documented; (C) some narrower version of (B) tied to a specific already-documented Claude Code mechanism, if one exists that this card has not found; (D) a different shape entirely. Which one, and if (B) or (C), what signal.
