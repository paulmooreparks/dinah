The workbench document "Convention counterexamples" is 293,701 bytes. The interface that serves it caps a response at 262,144. So a read returns nothing rather than a partial answer, and every agent told to read it before working gets nothing at all.

This was found on 2026-09-03 by an implement agent on dinah-332, which reported it plainly instead of working around it. The figures above were checked directly rather than taken from that report.

**Why this is worse than a large file being awkward.** That document is the mechanism this board uses to carry a lesson from the agent who learned it to the next agent who would otherwise repeat it. Three distinct ways of faking an armed guard were found in a single day, by three different agents, and each was written into that corpus as it was found. None of those entries can be read by anybody. The document has been growing all day and every entry added has made it less readable, so the corpus has been getting quieter the more it learns.

It also fails silently in the way this board keeps filing cards about. An agent that cannot read it does not see a refusal saying the document is too large; it sees nothing, and a dispatch telling it to read the conventions first is satisfied by having tried. Several dispatches today named that document explicitly and no agent reported a problem until this one did.

**What has to be settled.** Splitting the document is the obvious answer and it is not the only decision. What matters is that a reader looking for one shape can find it without loading the whole corpus, so the shape of the split is the question: by defect class, by the stage that catches it, by recency, or by something else. A split that produces five documents each near the ceiling has bought a few weeks.

Say also what happens when the next document approaches the limit, because this one did so without anybody noticing until a read failed. A listing already reports each document's size, so the information exists and nothing looks at it.

Weigh whether an entry earns its place at all. A corpus nobody can read is one failure; a corpus so long that a reader stops early is another, and the second is not fixed by splitting. dinah-266 and the operator's own instruction to keep dispatches readable both bear on this.

The operator has ruled against card explosion five times, so this card owns the whole question rather than filing a family. Whatever the sweep of the corpus turns up belongs here.

## Specification

Established facts (checked directly against the live workbench, 2026-09-04, before writing anything below):

**Every route to a workbench document, tested.** Four MCP calls reach a document body on this surface: `list_workbench_documents`, its deprecated twin `list_project_documents`, `get_workbench_document`, and its deprecated twin `get_project_document`. `list_workbench_documents(documents="Convention counterexamples", fields="id,title,body")` returned `documents: []` with `_meta.total_matched: 1, returned: 0, truncated_by: "max_bytes"` — no error, no message, an empty array standing where a document should be. `list_project_documents` with the same arguments returned the identical shape. `get_workbench_document(id=47, fields=body)` and `get_project_document(id=47, fields=body)` both returned the full body; the workbench-document call's result ran to 333,993 characters and was written to a side file by the calling harness rather than refused by the MCP layer, which is the harness's own token guard and not evidence of any ceiling on this route. Neither `get_*` schema documents a byte ceiling; both `list_*` schemas document "Default 48000, ceiling 262144" on the response. So exactly two routes exist, one refuses nothing and serves the whole document, the other returns an empty result once the response would exceed 262,144 bytes, silently, for any field selection that requests `body`.

**The document today.** "Convention counterexamples" (workbench document id 47) is 329,829 bytes as of this reading, already past the 293,701 bytes the card was filed against and past the 262,144-byte ceiling by 25%. It is a flat, chronological, append-only list of 162 entries, each a `## ` heading followed by a `**Wrong:**` / `**Right:**` pair (occasionally a `**The test:**` line). No sub-grouping, no category headings, no table of contents. The most recent entry is dated in its own title, "(dinah-369, 2026-09-04)" — today.

**The other four documents on this workbench, checked against the same ceiling.** Prose standard: 15,831 bytes. Go style standard: 12,389 bytes. Working safely against the operator's own data: 3,550 bytes. Translation staleness contract: 36,234 bytes, the largest of the four and still only 14% of the 262,144-byte ceiling. None is within reach of the ceiling; none needs this card's repair.

**Where the corpus is named.** Exactly three column instruction blocks tell an agent to read this document, none of them naming a route: Spec (`ca3badf49985`, line 113, lowercase "the convention counterexamples"), Agent Design Review (`0d86ad99cdbc`, line 25, hyphenated "the convention-counterexamples document"), Agent Code Review (`4b38abe7ebd5`, line 106, the exact quoted title "Convention counterexamples", the only one `check_instructions` finds by an exact-title search because the other two paraphrase it). Agent Code Review's block additionally says not to read it end to end and to report which entries were checked; none of the three names which tool call actually reaches the document, so an agent free to choose reasonably reaches for `list_workbench_documents` (the browsing call) and gets nothing, with nothing telling it that `get_workbench_document` was the other option.

**Why the card's own title overstates the finding, restated from the two corrections already on the card.** The document is not unreachable; `get_workbench_document` reaches it in full, and a code-review agent on dinah-332 used it that way, one command away from where a previous agent had stopped. What is real: one route (`list_workbench_documents`/`list_project_documents` with `body` requested) fails silently past the ceiling, and nothing routes an agent that hits it toward the route that works, so the failure reads as "this document cannot be read" rather than "this call cannot serve it."

## Scope: what this card does not reach, and why

`list_workbench_documents` and `list_project_documents` are Andoneer platform MCP tools. Their implementation is not in this repository; a `grep -ril "list_workbench_documents" --include="*.go" .` over the whole dinah checkout returns nothing, because this checkout is the Dinah CLI, and Andoneer is a separate, private platform repository this workbench's agents have no code access to and no git worktree convention for. Making the failing route refuse with a message naming the size and pointing at `get_workbench_document` — the cheapest of the three candidates the card asks to weigh — is a change to that platform's server code, and no agent working this card, in this worktree convention, on this workbench, can make it.

**Decision (D1).** This card does not attempt the server-side refusal-message fix. It is out of reach of the codebase and the tools this workbench's agents have. Recorded here rather than silently dropped, because the card asked for the candidate to be weighed rather than assumed away. If the operator wants that route hardened, it is a card against the Andoneer platform's own project, not this one; nothing here files it, since filing it is a judgment call about a different project's backlog and not a decision this card's implementation needs made.

## Decision (D2): rotate by chronological position, not by defect class

The card's own text treats "split by defect class, by the stage that catches it, by recency, or something else" as the open question. It is closed here.

The corpus is append-only and un-categorized today: 162 entries, zero existing headings above the per-entry `##`, added one at a time as reviews find them, with no author ever having assigned a category. A split by defect class or by catching stage requires building a taxonomy over 162 uncategorized entries and then maintaining it: every future append needs a classification decision before it can be filed, and a misclassified entry becomes exactly the kind of defect this corpus exists to catch (a reader who thought they searched the whole set searched one shelf of it). A split by chronological position needs no classification, ever: new entries always go at the tail of whichever part is currently open, and the only decision at append time is a size comparison, not a judgment call. Given that this document has already generated one card over an unwatched size, favor the split that removes size-watching from being a separate task and folds it into the append step itself. That is rotation, not taxonomy.

This does cost the thing the card's description raised in its defence of splitting by shape: "a reader looking for one shape should not have to load the whole corpus." Rotation does not deliver that; a reader hunting a specific entry still has to open however many parts exist. That cost is accepted here because a taxonomy strong enough to deliver it needs source-level review judgement this card cannot manufacture safely over 162 entries in one pass, and a wrong taxonomy is worse than none: it teaches a reader where to stop looking.

## Decision (D3): rotation threshold is 200,000 bytes per part

262,144 bytes is the hard ceiling `list_workbench_documents`/`list_project_documents` enforce. 200,000 bytes leaves 62,144 bytes (24%) of headroom below it, so a part that crosses the threshold mid-append still has room to finish the entry being written before the next append has to roll to a new part. Any single entry seen in the existing corpus is well under that margin (the largest visually is a few thousand bytes); an entry that alone approached 62,144 bytes would be its own defect, not something this threshold needs to plan for.

## What Implement does

**Do not use the entry count or line numbers below as literal cut points.** They describe this document as read on 2026-09-04, at 162 entries; more will have been added by review agents in the ordinary course of work between now and Implement's turn. Recompute against the live document at the time of the split, using the same method: fetch the current "Convention counterexamples" body, split it into entries at `^## ` boundaries, and accumulate entries into "part 1" until adding the next entry would push the accumulated byte count past 200,000; roll to "part 2" at that point and continue, repeating the rule for further parts if the corpus is large enough to need them. Applied to the 162-entry, 329,829-byte body read for this spec, that method cuts before entry 108 of 162 (the heading "A vocabulary rename applied to every occurrence of the word, including the ones that were ordinary English"), producing a first part of about 202,952 bytes (entries 1-107) and a second of about 126,811 bytes (entries 108-162) — both under the 262,144-byte ceiling. Treat this as a worked example of the method, not as the answer to apply blindly.

1. **Capture a pre-split snapshot before changing anything.** `get_workbench_document(id=47, fields=body)`, saved somewhere Test can diff against (a comment, a scratch file referenced in the handoff, or equivalent) — not this spec's own snapshot, which is already stale by the time Implement runs. This is the corpus's own lesson (its entry "A before-and-after coverage claim whose 'before' is counted on the 'after' tree") applied to itself: a before/after claim about a moving document has to capture "before" at the moment before the move, not at spec time.
2. **Split at the computed boundary(ies)** into documents titled "Convention counterexamples 1", "Convention counterexamples 2", and so on in appended order. Preserve every entry's heading and body text verbatim, in the same order, across the parts; nothing is reworded, recategorized, or dropped.
3. **Reuse document id 47 for "Convention counterexamples 1"** (rename in place, replace its body with the first part) rather than creating a fresh id, so anything already holding id 47 keeps pointing at real content. Create new documents for part 2 onward.
4. **Head each part with a short pointer, not a repeated preamble.** Part 1 keeps the corpus's existing opening paragraphs (the collection's purpose and the entry-writing convention for anyone about to add one) and gains one line stating it is part 1 of however many parts exist and naming the next part's title. Part 2 onward opens with a one- or two-line pointer back to "Convention counterexamples 1" for the purpose and convention, states its own position among the parts, and — only on the last (currently-open) part, the one new entries actually land in — restates the rotation rule from Decision D3 in one sentence: check the running byte count before appending; if the new entry would push this part past 200,000 bytes, create the next part instead and append there. That sentence moves with the tail as parts roll, so it is never duplicated across more than one document at a time.
5. **Update the three column instruction blocks** (Spec `ca3badf49985`, Agent Design Review `0d86ad99cdbc`, Agent Code Review `4b38abe7ebd5`) to replace their single-title reference with: read every workbench document whose title starts with "Convention counterexamples" — use `list_workbench_documents(documents=...)` filtered by title prefix, or scan the full listing, to enumerate however many parts currently exist rather than assuming a fixed count — and fetch each one with `get_workbench_document(id=...)`, never with `list_workbench_documents`/`list_project_documents` requesting the `body` field, which returns an empty result with no error once a document's body exceeds 262,144 bytes. Keep each column's existing surrounding guidance (Agent Code Review's "match entries against surfaces touched" scoping, Spec's placement inside its prose-standard paragraph, Agent Design Review's placement inside "read the documents that govern the surface") intact; only the naming-and-routing sentence changes.
6. **Do not touch the other four workbench documents.** None is within reach of the ceiling (§ Established facts); this card's repair does not extend to them.

## What still fails after this card

- The underlying platform behavior — `list_workbench_documents`/`list_project_documents` returning an empty result with no error once a document's body would exceed 262,144 bytes — is unchanged. Any future document on this or another Andoneer-managed workbench that grows past that ceiling hits the same silent failure until the platform's own code changes (Decision D1).
- Rotation defers the size problem per part; it does not remove it. The currently-open part (part 2 in the worked example above, about 127,000 of its 200,000-byte budget already spent) will itself need to roll to a further part once enough new entries land in it. The mechanism for that is the one sentence placed on the open part in step 4, which depends on whoever appends the next entry actually reading and following it; nothing enforces the check mechanically.
- No taxonomy was built. A reader hunting one specific defect shape still has to open every part rather than one, exactly the cost Decision D2 accepted in exchange for not needing an ongoing classification judgment.
