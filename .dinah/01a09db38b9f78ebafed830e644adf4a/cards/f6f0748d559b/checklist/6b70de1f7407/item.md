note: "Round 1 published the bare name and argued that the editor would resolve it. Agent Design Review defeated that argument on 2026-09-11 and it does not survive re-reading, which I did against `@types/vscode@1.101.0` myself. The `command` field's own doc comment reads \"The command used to start the server. Node.js-based servers may use `process.execPath` to use the editor's version of Node.js to run the script\", which says nothing about a system path and whose one hint points the other way, at handing the editor a path that is already resolved. The class comment says the process \"will be spawned as a child process of the extension host and by default will not run in a shell environment\", which takes the shell away as the resolver without naming a replacement. The sentence round 1 leaned on, \"Must be available on your system path or contain its full path\", is on the MCP configuration reference and is a requirement placed on a value a reader types into `mcp.json`, not a statement about what the editor does with a string an extension hands it through a different API. The bridge between the two was \"no page promises they resolve a command differently\", and an argument from silence is exactly what the operator's standing rule refuses.\n\nSo the question is dissolved rather than answered. Whichever of the two readings of that requirement is right, a full path satisfies both, and no page has to promise anything about name resolution because no name is published. The route is D-10's: the binary reports where it is, and the extension publishes what it was told. The cheaper alternative Agent Design Review offered, publishing only where an absolute `dinah.path` setting is in hand, is rejected because it turns the common case off. A reader who installed the binary on their path and never opened settings is the reader this feature is for, and telling them in the README to set a path they should not have to know is a worse product than asking the binary a question it can answer."
