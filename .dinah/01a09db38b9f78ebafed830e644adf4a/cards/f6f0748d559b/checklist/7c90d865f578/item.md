note: "Round 1 registered the provider only when `binary.state === \"ok\"`, and Agent Design Review pointed out that a reader who opens the window before installing the binary then gets no registration at all, with nothing telling them so.\n\nRegistering unconditionally removes the special case rather than documenting it. The registration itself publishes nothing; `provideMcpServerDefinitions` is what answers, and it answers with an empty array whenever D-11's preconditions are unmet, which AC-15 pins. The API's own doc comment asks for this shape anyway, saying extensions \"should call `registerMcpServerDefinitionProvider` during activation\" so that the editor can offer its refresh action when a new provider appears.\n\nWHERE THE ANSWER IS COMPOSED, corrected at Spec round 3, 2026-09-11. This decision's text said the callback decides, which round 2's spec took literally and which Agent Design Review refused: `test/unit/layers.test.ts:161-191` puts `extension.ts` out of reach of every unit test, so a ladder written there could not be exercised by anything this card allows. The callback still answers, and it answers by calling `publishedMcpServers` in `mcpServers.ts` with the binary state, the setting's value and the targets. Every rung of the refusal is in that pure function, and `extension.ts` holds the setting read, the emitter, the mapping to vscode values and the registration call.\n\nWhat this does not fix, and the spec says so rather than leaving it to be discovered, is that the binary is resolved once per window. `resolveBinary` is called at `extension.ts:363` and nowhere else on `65a80ad`, so a reader who installs the binary after activation is in the same position for the tree, the status bar and the diagnostics as for this, and the window reload that fixes one fixes all of them. Re-resolving the binary on demand is a change to the extension's own lifecycle that would touch every one of those surfaces, so it belongs to a card about that rather than to this one."
---
The provider is registered unconditionally at activation, and what to publish is decided lazily when the editor asks, by a pure function the callback calls.
