note: "Three consequences of D-9, each settled here so the implementer has no question to ask.\n\nGo documents `os.Executable` as returning \"an absolute path unless an error occurred\", so the failure case is an error and the field is then absent rather than empty, through `json:\"executable,omitempty\"`. An absent field and an older binary that never learned to send one are indistinguishable to the extension and are treated alike: it publishes no definitions at all. There is deliberately no fallback to the bare name, because a fallback would reinstate the inference D-9 exists to remove and would do it exactly where nobody is watching. The reader who hits this loses a convenience and can still register `dinah mcp` by hand in their own `mcp.json`, which is what they would have done before this card existed.\n\nGo documents two caveats beside that sentence and this card acts on neither. Corrected at Spec round 3, 2026-09-11, on the Agent Design Review finding that round 2 quoted one of them and overreached on it while ignoring the one this card's usage actually meets. The full text reads: \"Executable returns the path name for the executable that started the current process. There is no guarantee that the path is still pointing to the correct executable. If a symlink was used to start the process, depending on the operating system, the result might be the symlink or the path it pointed to.\"\n\nOn the symlink caveat: either answer is an absolute path to something runnable, which is all this needs, so `filepath.EvalSymlinks` is not called. Round 2 added a second reason, that calling it \"would break the case where the symlink is the stable name and the target is a versioned file\", and that reason is cut, because not calling `EvalSymlinks` does not preserve the symlink. The same documented sentence declines to promise which of the two you get, and Linux hands back the target through `/proc/self/exe`.\n\nOn the staleness caveat: the path is not promised to still point at the correct executable, and this card's usage meets that. The extension resolves the binary once per window at activation and the editor may spawn the published command hours later, so a reader who replaces or moves their binary in between gets a spawn failure reported by the editor, and nothing in the extension notices or explains it. That is accepted rather than handled. Handling it means re-resolving the binary on demand, which D-14 records as a change to the extension's whole lifecycle rather than to this feature.\n\nThe field does not reach the human rendering. `render.go` is not edited and no new key is added to the CLI's own message catalogues, because the field exists for a machine caller and a reader asking `dinah version` is asking what the binary is rather than where it is. That also keeps this card away from the fixtures that key on line numbers in `render.go` and `docs/quick-start.md`, which move together when either is edited."
---
A binary that cannot say where it is publishes nothing, the reported path is used as reported without symlink resolution, and the human rendering of `dinah version` does not change.
