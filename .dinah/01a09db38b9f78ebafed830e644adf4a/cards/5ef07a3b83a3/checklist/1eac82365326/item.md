What cannot be kept is the folder name. `IsWorkbenchID` (internal/bench/storage.go:245) requires 32 lowercase hex decoding to a UUIDv7, and its own comment says the entity and workbench predicates \"are disjoint by their lengths alone, which is what makes a legacy workbench directory and a migrated one impossible to confuse\", so a 12-hex name is a legacy name by construction. `dinah check --migrate-container` reports it as `legacy-name` and renames it; reproduced twice, once to `01a09b8d3243700eba5ab248775cbe93` and once to `01a09ba1476e74ff9bf61317a964c64c`. There is no flag anywhere that preserves the old name.\n\nA name embedding the old identifier is legal, and I tried it rather than assuming: a directory called `149f228d48c37a2b8000000000000000` satisfies the predicate and the tool opened the workbench from it without complaint. It is still the wrong answer. The first 48 bits of a UUIDv7 are the milliseconds it was minted at, so that name claims a creation instant of 2688-07-02, where the name actually minted decodes to 2026-09-13. A directory that lies about its own age to smuggle a reference through is worse than a sentence, and a sentence does the job: the workbench's standing text names the Andoneer board identifier `149f228d48c3` as the board this workbench continues, which is readable, true, and in the place a reader is already looking.\n\nThe column directories came through untouched, verified by listing all fourteen after each run, and column identity is the one that matters here because the hold table, every item's stored column and every gate reference are keyed on it. Consequence: no path naming `149f228d48c3` as a directory may outlive step 1, on the card or in any criterion, so both address the workbench by discovery instead."
