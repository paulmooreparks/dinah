note: "This decision covers startup cases 2 and 3 together, which is a widening from what it first ruled. It first split case 3 alone, on the ground that a `--root` and a `--workbench` written into one registration and disagreeing is a contradiction in a file while a walk that landed outside the root is nobody's instruction. Agent Design Review then found case 2 sitting one paragraph above it and not applying the same rule: with a root named, `--workbench` pointing at a directory that holds no workbench served quietly, while `--workbench` pointing at a real workbench outside the root exited 2. The gentler answer went to the worse pointer, and today's behaviour for the first typo changed without the spec saying so, since with no root named the same command exits.\n\nBoth cases now split on the same line, which is whether an explicit pointer named the workbench. An explicit pointer is `--workbench` or `DINAH_WORKBENCH`. Everything else, meaning the ancestor walk and the stored default in the user config, demotes to no default, writes one line to stderr from `mcp.no-default`, and serves.\n\nWhy that line and not another. Startup discovery climbs from the server process's working directory, an MCP client chooses that directory, and a head that exited over what the walk found would start on one machine and refuse on another with the same registration. A pointer somebody wrote down carries no such dependency, so refusing it while whoever wrote it is still reading stderr costs nothing and catches the typo.\n\nThe head has what it needs at both sites. `session` resolves `--workbench` and `DINAH_WORKBENCH` into one override value and its rung before `open` runs, so a non-empty override is the explicit pointer, and `bench.DiscoverSource` raises `dinah.no-workbench` from that override branch alone; the other three discovery refusals, `dinah.ambiguous-workbench`, `dinah.no-configured-workbench`, and `dinah.no-workbench-found`, are raised only from rungs nobody wrote into the registration. For case 3 the resolved default carries its rung out of `bench.ResolveWorkbenchSource`.\n\nWhy this is mine rather than the operator's. The reviewer named reconciling as the spec author's option in both cycles, the ruling turns on facts about this repository rather than on a preference, and the behaviour it produces is drawn in section 4 of the UX sketch, which the operator ratifies at his own station. Nothing here reopens D-1 or D-2.\n\nThe consequence for the help page is that `beyondChecks[\"mcp\"]` still carries both names in the same order, since the explicit branch of case 3 still refuses at startup. Case 2's explicit branch refuses `dinah.no-workbench`, which is not in that list, because it belongs to workbench discovery rather than to `mcp` and no other command's check list carries it either. AC-12 holds case 3's exiting branch, AC-19 its serving branch, and AC-25 both halves of case 2.\n\nRepository claims verified for this decision: 5 (the `bench.Source*` constants and that `ResolveWorkbenchSource` returns the rung an answer came from, that `session` holds the resolved override and its rung before `open` runs, that `DiscoverSource` raises `dinah.no-workbench` only from the override branch and the other three refusals only from the walk and the config rungs, that startup discovery climbs from the process's working directory, and that a throwaway build launched inside a workbench outside the root serves and answers an unqualified `status` with `dinah.no-workbench-found`)."
