note: "Refusal names on this board come from the contract's own vocabulary rather than being invented at the call site, so both names are declared once beside their siblings in internal/contract/contract.go, added to `contract.Introduced`, given an entry in `contract.Shapes` in internal/contract/shape.go, and spelled from those constants everywhere. The Go style standard's rule 5 says the same thing.\n\nThree existing names were weighed and none fits. `dinah.no-workbench-found` describes an upward walk from a starting directory, which is not what a missing root is, and the contract already separates it from `dinah.no-workbench` on precisely that ground, with the comment saying one template cannot honestly describe both a path the caller named and a search that reached the root of the filesystem. `dinah.workbench-not-applicable` is the precedent for refusing a pointer that does not apply rather than ignoring it, and it is about init rather than about a bound. `dinah.unknown-path` is the third and the closest, since it also refuses a filesystem path the caller named that is not there, which is what `check.attach.1` uses it for and what internal/verb/beyond.go raises it as; it loses because its sentence reads \"nothing in this workbench answers to {detail}\" and a root is not a thing in a workbench.\n\nThe order matters because a single startup can trip more than one of these. A root that does not exist and a `--workbench` pointing outside it are both true at once, and a corpus entry on this board records what happens when two mandatory refusals share one slot with no rule saying which comes back. The spec therefore numbers the startup checks and numbers the per-call checks, `beyondChecks[\"mcp\"]` carries the startup pair in that order so `dinah help mcp` prints the same order the code runs, and AC-20 and AC-21 exercise a request that trips two checks at once on each of the two surfaces.\n\nThe two sentences are drafted together in section 7 of the UX sketch, so a reader moving from one to the other gets the same class of guidance rather than one message naming the path and the other naming nothing.\n\nRepository claims verified for this decision: 5 (the `Introduced` list and the comment separating `dinah.no-workbench` from `dinah.no-workbench-found`, the existence and purpose of `dinah.workbench-not-applicable`, the sentence and raise site of `dinah.unknown-path`, the `contract.Shapes` guard that fails over an undeclared refusal name, and that `dinah help mcp` renders its refusal table from `beyondChecks`, confirmed by a throwaway build)."
